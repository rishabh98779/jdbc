The Complete Java System: From Data Input to a Working Application

One application, many technologies. This chapter builds the mental model that every later chapter refers back to.

1.1The question this book answers

Here is the question. It is short, and it is the reason this book exists rather than a stack of separate revision sheets:

THE CENTRAL QUESTION

How do separate Java technologies work together to turn incoming data into a usable application, store information persistently, and display useful results to a user?

A student who has just finished a semester of Java can usually answer each part of that question alone. Streams read and write data. JDBC talks to databases. Swing draws windows. Maven builds projects. Each answer is correct and each is nearly useless on its own, because in a real program these things are not separate. A button press causes a query; a query returns rows that become objects; those objects are rendered; the same data is also written to a log file; a thread produced the data in the first place. The technologies are a system.

So this chapter does not explain any API in depth. It does something more important: it shows you the system, names every component in it, and explains why each technology is present. By the end you should be able to sketch the whole application from memory. Every later chapter fills in one box of that sketch.

CORE CONCEPT

The organising idea of this book is one connected Java application. Every technology you will study is introduced twice: first on its own terms, then in the place where the application actually needs it. If you ever lose the thread, come back to Diagram 1 and find your current topic in it.

1.2What BasinWatch is trying to accomplish

BasinWatch is an offline floodplain operations console. A basin is a river catchment area; when rain falls and water levels rise, some districts flood before others, and a control room has to decide where to send limited equipment. BasinWatch simulates that situation on a desktop so a student or planner can practise the decisions without any real risk.

The operator's job, in the project's own words, is to watch a schematic basin map as rain and water levels change, review severity-ranked zone alerts, dispatch pumps, levee crews and evacuation teams to concurrent missions, see what resources remain available, then save the session, close the application, and restore the model and active operations later.

What enters the system

  • Simulated station observations: rainfall in millimetres and observed water rise in centimetres, for six named zones.
  • Simulation pulses marking the passage of a time interval.
  • Operator commands: start, pause, step, inject a storm cell, dispatch, save, restore, export a report.
  • Selection events: which zone the operator is inspecting.

What leaves the system

  • A live map of six zones coloured by risk level.
  • A ranked activity timeline and a list of active field operations.
  • A resource board showing available and committed units.
  • Persistent artefacts: an operational log, a typed binary archive, session saves and readable reports.
  • Optional queryable history in a local SQLite database.

Six zones are monitored. Each has a position on a two-by-three schematic grid, an initial water level in metres, and a number of exposed residents. Risk is derived from the water level by fixed thresholds: below 1.7 m is NORMAL, 1.7 m and above is WATCH, 2.6 m and above is WARNING, and 3.6 m and above is CRITICAL.

BASINWATCH IN PRACTICE

Those thresholds are real code, not invented for the book. They appear in BasinZone.assessRisk(double):

static RiskLevel assessRisk(double waterLevelMeters) {
    if (waterLevelMeters >= 3.6) return RiskLevel.CRITICAL;
    if (waterLevelMeters >= 2.6) return RiskLevel.WARNING;
    if (waterLevelMeters >= 1.7) return RiskLevel.WATCH;
    return RiskLevel.NORMAL;
}

The six layers, in the order data meets them

  1. The operator and the interface. BasinWatchApp.main sets the system look and feel and then hands control to the event-dispatch thread with SwingUtilities.invokeLater. From that moment the MainFrame owns the window, and only the event-dispatch thread may touch Swing components.
  2. Application commands. The interface never manipulates the model directly. It calls a narrow set of methods on BasinEngine: start(), pause(), step(), dispatch(...), injectStorm(...), save(...), load(...), exportReport(). Most return a CompletableFuture, so the interface can ask for work and keep painting.
  3. The domain and engine layer. BasinModel is the aggregate root: it owns the six zones, the mission registry, the recent-activity ring buffer and the resource allocator. It enforces invariants and produces immutable snapshots. Three ResponseWorker tasks consume events and apply them.
  4. The sensor input path. A dedicated SensorFeed thread encodes observations as text lines and writes them into a PipedWriter. A separate SensorIntake task reads them through a BufferedReader over a PipedReader, validates each record, and places accepted events into a bounded EventBuffer.
  5. File persistence. Four independent file responsibilities: a UTF-8 append-only operational log, a typed binary sensor archive, versioned session snapshots written through an atomic replace, and human-readable reports.
  6. The JDBC layer. An optional, single-threaded DatabaseService that writes accepted readings, mission lifecycles, resource allocations and operational events into a local SQLite file through parameterized SQL, and reads recent history back for the interface.

Notice that the file column and the database column both hang off the same point — accepted events — but they are not alternatives. Chapter 9 shows what each file is for; Chapter 14 shows what the database adds; Chapter 10 explains why an application would deliberately choose to have both.

1.4The seven questions the architecture must answer

An architecture is only useful if it answers concrete questions. These are the seven that matter for this application, with the verified answers.

Which component processes incoming data?

Observations arrive as text lines from the pipe. SensorIntake parses each line with SensorReading.parse, which validates the field count, the record type marker and every numeric range. A malformed record is reported and discarded — it does not stop the intake loop. Accepted events go into the bounded EventBuffer, and one of the three response workers takes them from there.

Where is Java I/O needed, and why?

In four genuinely different places, for four genuinely different reasons. The pipe carries observations between threads. The journal and reports give humans a readable audit trail. The archive keeps typed numeric measurements for later diagnosis. The snapshot store captures the whole session so it can be restored. Chapter 9 treats this as a design question rather than a list.

Why does JDBC exist in this application?

Because a file answers a different question than a database. A log file is a sequence of lines; asking "show me the 200 most recent readings for zone MIL, newest first" means reading and filtering the whole file. A database answers that with an index and a LIMIT. BasinWatch therefore keeps both, and the database is optional precisely because it is an addition rather than a requirement.

What does the Swing interface do?

Three things: it renders immutable snapshots, it collects operator intent, and it reports outcomes. It does no domain logic and no persistence. That separation is what makes the rest of the application testable without a window.

Which work happens on background threads?

Observation production (SensorFeed), intake (basin-sensor-intake), response processing (three basin-response-N threads), archiving (basin-sensor-archive), control commands (basin-control) and database writes (basin-database). Only rendering and event handling happen on the event-dispatch thread.

How does data survive the application closing?

Five ways, listed in Table 1.1. On a clean shutdown the engine also writes an automatic last-session.bws snapshot, so the next launch can restore the basin.

Where do the technologies interact, and where do they stay separate?

They interact at exactly two boundaries. The first is the accepted event: after the model has processed an event, the engine writes to the log, submits to the archive worker, and enqueues a database operation. The second is the published snapshot: the engine hands an immutable value to the interface, the only channel by which background work becomes visible. Everywhere else the layers are deliberately ignorant of one another: the model does not know about files, the repositories do not know about Swing, and the interface does not know about SQL.

IMPORTANT DISTINCTION

The engine publishes immutable snapshots, not live objects. A BasinSnapshot is a record whose constructor copies every list and map with List.copyOf and Map.copyOf. That single decision is why the interface can render data on the event-dispatch thread while workers continue to mutate the model — the snapshot cannot change underneath it.

1.6What is genuinely difficult here

It is worth being honest about which parts of this application are hard, because those are the parts worth understanding deeply rather than memorising.

Concurrency is hard because correctness is invisible. If two dispatches both read the same resource count as available, the bug appears only under load and only sometimes. BasinWatch's answer is a single short synchronized reservation that checks every required resource before decrementing any of them — an all-or-nothing operation. There is no way to observe the intermediate state, because there is no intermediate state.

Shutdown is hard because it is where resources leak. Stopping a feed thread, closing a pipe, waking waiting consumers, draining an archive queue, flushing a journal and writing a final snapshot must happen in the right order. The engine's closeEngine() does exactly this, and reports a timeout rather than pretending success.

Persistence is hard because the easy version is unsafe. Writing a file with ObjectOutputStream is two lines; making it safe means bounding the input size, filtering the classes that may be constructed, checking a format version, and validating the restored domain state. Chapter 8 walks through all four.

COMMON MISTAKE

The most common architectural mistake in student projects is letting the interface do the work. A button handler that opens a database connection, queries, and updates a label feels natural because it is one function in one file. It also freezes the window for the duration of the query, makes the logic untestable without a screen, and spreads SQL across the codebase. BasinWatch's rule — the interface asks, the engine decides, a worker executes, a snapshot reports — is the fix.

CHAPTER 2

Java Application Structure and Core Object Concepts

Objects, interfaces, inheritance, enums, records and validation — the vocabulary the rest of the book assumes.

2.1Why start with objects?

Every later chapter is about a mechanism — a stream, a query, a listener. Each mechanism operates on objects, and each is designed around an object concept. If a method takes an interface, the interface's design determines what the method can do. If a class is a record, it cannot be mutated. So the object model has to come first.

This chapter is not an introduction to writing classes. It is a tour of the specific object decisions BasinWatch makes, with the reason for each, plus the POJO-versus-JavaBean distinction that appears in the syllabus and matters the moment you meet a framework.

2.2Classes, objects, state and behaviour

A class is a template; an object is an instance of it. An object has state (its fields) and behaviour (its methods), and good design keeps state private so behaviour is the only route in.

DEFINITION

Encapsulation — keeping fields private and exposing only the operations that make sense, so an object can never be placed in an invalid state from outside.

BasinWatch applies this at several levels. BasinZone is package-private: only classes in com.basinwatch.domain may even refer to it. Its fields are private, and it exposes a small set of package-private methods — apply, pump, reinforceLevee, evacuate — plus snapshot(), which returns an immutable copy.

final class BasinZone {
    private final String id;
    private final String name;
    private double waterLevelMeters;
    private double lastRainMillimeters;
    private int exposedResidents;
    private boolean leveeReinforced;
    private long lastReadingTick = -1;
    private RiskLevel risk;

    boolean apply(SensorReading reading) {
        if (reading.tick() <= lastReadingTick) {
            return false;                     // a stale reading is rejected, not applied
        }
        lastReadingTick = reading.tick();
        lastRainMillimeters = reading.rainfallMillimeters();
        double runoffFactor = leveeReinforced ? 0.58 : 1.0;
        double rainfallContribution = reading.rainfallMillimeters() * 0.0014;
        double observedRise = reading.observedRiseCentimeters() / 100.0;
        waterLevelMeters = Math.min(8.0,
                Math.max(0.0, waterLevelMeters + (rainfallContribution + observedRise) * runoffFactor));
        risk = assessRisk(waterLevelMeters);
        return true;
    }
    // pump, reinforceLevee, evacuate, snapshot, restore, assessRisk ...
}
from BasinWatch, domain/BasinZone.java — state is private; behaviour is the only route in.

Three things in that listing deserve attention. First, the stale-reading guard: if the incoming tick is not newer than the last one applied, the reading is ignored and the method returns false. That is an invariant, not a nicety — without it, an out-of-order observation could reduce a water level. Second, the reinforced levee multiplies runoff by 0.58, which is a real domain consequence of an earlier operator decision. Third, the water level is clamped to the range 0 to 8 metres on every update, so the field can never hold a physically impossible value.

CONNECTION TO ANOTHER CONCEPT

That guard is why Chapter 20's trace can say "the observation was accepted" and mean something specific. A reading is accepted only if it is newer than the last one for that zone and the model changed as a result. The engine uses exactly that test when deciding whether to write the reading to the database.

2.3Interfaces as contracts

An interface declares what a type can do without saying how. In BasinWatch, the whole event system is built on one interface with four methods.

public interface BasinEvent {
    long tick();
    String zoneId();
    String category();
    String describe();
}

Three records implement it: SensorReading, SimulationPulse and DispatchRequest. They are radically different in content — a measurement, a time marker, an operator command — yet they all satisfy the same contract, so a single queue and a single process method can handle all of them.

2.4Polymorphism: one call, several behaviours

Polymorphism means the same call site behaves according to the actual type of the object. BasinModel.process is the clearest example in the project.

public synchronized List<String> process(BasinEvent event) {
    if (event == null) {
        throw new IllegalArgumentException("Event is required.");
    }
    ArrayList<String> messages = new ArrayList<>();
    if (event instanceof SensorReading reading) {
        applyReading(reading, messages);
    } else if (event instanceof SimulationPulse pulse) {
        applyPulse(pulse, messages);
    } else if (event instanceof DispatchRequest request) {
        applyDispatch(request, messages);
    } else {
        throw new IllegalArgumentException("Unsupported basin event: " + event.getClass().getName());
    }
    return List.copyOf(messages);
}
from BasinWatch, domain/BasinModel.java — pattern matching on the event type.

This is polymorphism expressed with pattern matching rather than with a method override. Both are valid; the choice here is deliberate. The model wants one place where the complete set of event types is visible, so that adding a fourth event type produces a compile-time-visible gap rather than a silently ignored class. The else branch throws, so an unknown event type is a loud failure rather than a silent no-op.

IMPORTANT DISTINCTION

Interface polymorphism (what the queue relies on) and dispatch polymorphism (what the model performs) are different things. The interface lets the buffer store any event without knowing its type. The instanceof chain is how the model decides which behaviour to run. You need both: the first for type safety, the second for behaviour selection.

2.5Inheritance: used narrowly and for a reason

Inheritance is the most over-used feature in student Java. BasinWatch uses it exactly twice, and both times because the superclass is a real framework contract rather than a convenience.

  • SensorFeed extends Thread. A feed has a genuine lifecycle to own: it must be started, it has a long-running loop, it holds a blocking pipe endpoint, and it must be interruptible and joinable.   • MainFrame extends JFrame, BasinMapPanel extends JPanel, DatabaseHistoryPanel extends JPanel. Swing is an inheritance-based framework: to be a component you must be a component. Overriding paintComponent is how custom drawing is done.

Everywhere else, composition is preferred. BasinEngine does not extend anything; it has an EventBuffer, a DatabaseService, a list of listener lists and an ExecutorService.

2.7Records: immutable values with no boilerplate

A record declares immutable data in one line. The compiler generates a canonical constructor, accessors named after the components, and correct equals, hashCode and toString.

public record SensorReading(
        long tick, String stationId, String zoneId,
        double rainfallMillimeters, double observedRiseCentimeters) implements BasinEvent {

    public SensorReading {                       // compact constructor: validation
        if (tick < 0 || !validIdentifier(stationId) || !validIdentifier(zoneId)
                || !Double.isFinite(rainfallMillimeters) || rainfallMillimeters < 0
                || rainfallMillimeters > 500
                || !Double.isFinite(observedRiseCentimeters) || observedRiseCentimeters < 0
                || observedRiseCentimeters > 200) {
            throw new IllegalArgumentException("Invalid sensor reading.");
        }
    }

    @Override public String category() { return "OBSERVATION"; }

    public String encode() {
        return String.format(Locale.ROOT, "READ|%d|%s|%s|%.3f|%.3f",
                tick, stationId, zoneId, rainfallMillimeters, observedRiseCentimeters);
    }

    public static SensorReading parse(String line) {
        String[] fields = line.split("\\|", -1);
        if (fields.length != 6 || !"READ".equals(fields[0])) {
            throw new IllegalArgumentException("Malformed sensor observation.");
        }
        try {
            return new SensorReading(Long.parseLong(fields[1]), fields[2], fields[3],
                    Double.parseDouble(fields[4]), Double.parseDouble(fields[5]));
        } catch (NumberFormatException ex) {
            throw new IllegalArgumentException("Sensor reading contains an invalid number.", ex);
        }
    }
}
from BasinWatch, domain/SensorReading.java — a record that validates on construction.

Three patterns in that listing are worth naming, because they recur throughout the book.

The compact constructor validates. A record's canonical constructor can be written without repeating the parameter list, and any exception thrown there prevents the object from existing. This is why parse can be trusted: if it returns a SensorReading, the ranges are already correct. Validation happens at the boundary, once, instead of being re-checked by every consumer.

Keeping them next to each other in the same class is what makes the wire format maintainable. Chapter 7 follows that format through the pipe.

Immutability makes the object safe to share. A SensorReading can be handed from the feed thread to the intake thread to a worker thread with no synchronization at all, because no thread can change it.

2.8POJO versus JavaBean

DEFINITION

CHAPTER 3

How Java Components Communicate

Method calls, shared objects, streams, events, queues and database operations are six different mechanisms. This chapter separates them.

3.1The problem with saying "they communicate"

When you describe an application it is tempting to say that components "talk to each other" and leave it there. That sentence hides six distinct mechanisms with completely different properties. A method call is synchronous and immediate. A stream carries bytes or characters in one direction and can block. A queue decouples two threads in time. An event listener inverts control. A database operation crosses an execution boundary. An interrupt is a cooperative request, not a command.

Choosing the wrong one produces the classic failures: a frozen interface, a race condition, a lost update, a deadlock, a silent data loss. So this chapter names each mechanism, states its properties, and shows where BasinWatch uses it — and, just as importantly, where it does not.

3.2Mechanism one: the method call

The ordinary method call is synchronous, in-process, typed and immediate. The caller waits, the callee runs on the caller's thread, and arguments and return values are checked by the compiler.

BasinWatch uses method calls for everything that is fast and deterministic. BasinModel.process(event) is a method call. BasinZone.assessRisk(waterLevel) is a method call. SessionSnapshot.from(snapshot) is a method call. None of them touches a disk, a network or a thread.

CORE CONCEPT

The design rule the project follows is: a method call may not block on external work. Anything that reads a disk, waits for another thread, or talks to a database is moved behind a different mechanism — a future, a queue, or a background thread. That is why the model's methods are short and why the engine's file and database work is submitted rather than performed inline.

3.3Mechanism two: shared objects under a monitor

Two threads can communicate simply by reading and writing the same object. The cost is that every such access needs protection, and the protection is what creates the bugs.

ResourceAllocator is the canonical example: a shared, finite inventory read and written by several response workers.

public synchronized boolean tryReserve(Map<ResourceType, Integer> request) {
    validateRequest(request);
    for (Map.Entry<ResourceType, Integer> entry : request.entrySet()) {
        if (available.get(entry.getKey()) < entry.getValue()) {
            return false;                       // nothing has been changed yet
        }
    }
    request.forEach((type, amount) -> available.put(type, available.get(type) - amount));
    return true;
}
from BasinWatch, domain/ResourceAllocator.java — check every requirement, then decrement.

Read that method twice. The first loop only checks. If any single requirement cannot be met, the method returns false having changed nothing at all. Only after every requirement has been confirmed does the second loop decrement. That is what makes the reservation all-or-nothing: there is no moment at which a caller could observe a partially reserved state, because the entire method holds the object's monitor from start to finish.

CONNECTION TO ANOTHER CONCEPT

This is also the project's deadlock-avoidance strategy, which its own architecture notes describe directly: one short inventory monitor, no I/O inside it, no nested acquisition of another lock, and a stable policy. A lock-ordering cycle requires two locks acquired in opposite orders by two threads; with one lock, that cycle cannot form.

3.4Mechanism three: streams

A stream is a one-directional channel that carries a sequence of bytes or characters, with its own buffering and blocking behaviour. It is the subject of all of Part II, so here we only need its role in the architecture: it is how the feed thread hands data to the intake thread without either one knowing the other's class.

3.5Mechanism four: the queue with condition waiting

A queue decouples producer and consumer in time. The producer does not wait for the consumer to be ready; the consumer does not poll. The mechanism that makes this work is wait() and notifyAll() under a monitor, and it must be written carefully.

public synchronized boolean put(BasinEvent event) throws InterruptedException {
    if (event == null) {
        throw new IllegalArgumentException("Event is required.");
    }
    while (!closed && events.size() == capacity) {     // condition re-checked in a loop
        waitingProducers++;
        try {
            wait();                                    // releases the monitor while waiting
        } finally {
            waitingProducers--;
        }
    }
    if (closed) {
        return false;
    }
    events.addLast(event);
    notifyAll();                                       // wake every waiter to re-check
    return true;
}
from BasinWatch, engine/EventBuffer.java — a correct condition-wait loop.

Four properties of that code are the whole lesson, and they appear in every correct condition-wait implementation:

  1. Wait inside a loop, never inside an if. A thread that wakes up is not guaranteed that its condition is now true — another consumer may have taken the item first. So the test is repeated.
  2. Hold the monitor. wait() may only be called by a thread that owns the object's monitor. The synchronized keyword on the method provides it.
  3. Signal with notifyAll(), not notify(). Producers and consumers wait on the same monitor, so waking one arbitrary thread might wake a producer when only consumers can progress. notifyAll() lets every waiter re-check, and the ones that cannot proceed go back to waiting.
  4. Count the waiters. waitingProducers and waitingConsumers are incremented and decremented around the wait in a finally block, so the diagnostic view stays accurate even if the thread is interrupted. These counters are diagnostics, not synchronisation — an important distinction this chapter returns to.
IMPORTANT DISTINCTION

wait() releases the monitor; sleep() does not. This single sentence explains most of the confusion around Java threading. A waiting thread lets another thread enter the synchronized region; a sleeping thread keeps the lock and blocks everyone else. BasinWatch uses wait() for coordination and Thread.sleep(...) only for cadence — the feed's interval and the shutdown quiescence check — never as a signalling device.

COMMON MISTAKE

Using Thread.sleep() to wait for another thread's work, and using a flag variable polled in a loop, are the two most common substitutes for condition waiting. Both are wrong for the same reason: they guess at timing instead of reacting to state. A sleeping consumer may sleep too long (wasted latency) or too little (busy spinning), and a polled flag cannot wake anybody at the moment the state changes.

3.6Mechanism five: events and listeners

An event listener inverts control: instead of a component asking for data, the component declares interest and is called when something happens. In BasinWatch the interface registers listeners on the engine.

The listener contract is therefore: I may be called from any thread; I will not touch Swing directly. Chapter 16 examines that hand-off in detail.

3.7Mechanism six: database operations

A database operation is the only mechanism in this list that leaves the Java execution model. Even with an embedded SQLite file, the operation involves a different execution path: SQL is parsed and planned, rows are read through a cursor, and failures arrive as SQLException rather than as ordinary Java exceptions.

  • Reads return a future. loadHistory returns a CompletableFuture<List<DatabaseHistoryEntry>>, so the interface can attach a callback without blocking.

3.9The two boundaries, restated

Chapter 1 claimed that the technologies meet at exactly two boundaries. With the six mechanisms named, that claim can be made precise.

Boundary one — the accepted event

A worker has just applied an event to the model. At this single point the engine fans out: it appends to the journal, submits to the archive worker, and enqueues a database operation. Everything downstream of that fan-out is persistence, and none of it can change the model.

Boundary two — the published snapshot

The engine calls every registered snapshot listener with an immutable value. That call crosses from background threads to the event-dispatch thread and is the only channel by which background work becomes visible to a human.

What Is a Stream?

The stream abstraction, source and destination, direction, and the four hierarchies that organise the whole java.io package.

4.1The problem a stream solves

Suppose you want to copy a large file. You could read the whole thing into memory as a byte[] and then write it out. That works for a small file and fails for a large one, because the file must fit in memory. It also fails for data that has no end yet — a network socket, a pipe from another process, or a sensor feed that runs for hours.

A stream is the abstraction that solves this. Instead of handling all the data at once, you handle it in pieces: read some, process it, read some more. The stream hides whether the bytes come from a file, memory, a socket or another thread. That is why one read() method can serve a disk file and a pipe.

DEFINITION

Stream — an ordered, one-directional sequence of data with a source or a destination, consumed or produced incrementally rather than all at once.

CORE CONCEPT

Three properties define every stream in java.io, and every question about streams reduces to them:

  1. Direction. Input or output — read or write, never both.
  2. Unit. Bytes (8-bit) or characters (16-bit, with an encoding).
  3. Source or destination. A file, memory, a pipe, or another stream.

Name those three and you have named the class you need.

4.2Source, destination and direction

Direction is the first thing to fix, because it determines which of two class families you are in. A source is where data comes from: for an input stream, the source is the file or pipe you read. A destination is where data goes: for an output stream, the destination is the file or pipe you write.

The naming is always from the program's point of view, not the device's. A FileInputStream reads into the program from a file. A FileOutputStream writes out of the program to a file. This is the single most common source of confusion for beginners, and it disappears once you say the direction aloud.

4.3Byte streams versus character streams

This is the first real decision you make with any stream, and it is a decision about meaning rather than performance.

CONCEPT EXPLAINED FURTHER

Why are characters 16-bit when bytes are 8-bit? Because Java's char is a UTF-16 code unit, chosen so that the common characters of the world's writing systems fit in one unit. The bridge between a 16-bit character and 8-bit storage is the charset — UTF-8, UTF-16, ISO-8859-1 and so on. A character stream always uses one, either explicitly or through the platform default.

IMPORTANT DISTINCTION

Encoding is not encryption and it is not compression. Encoding is a reversible mapping from characters to bytes. Nothing is hidden and nothing is made smaller — UTF-8 often makes text larger than a single-byte encoding would.

4.4The four hierarchies

The entire java.io package is organised around four abstract roots, and every concrete class descends from exactly one of them.

Two things are worth noticing in that diagram.

There is a symmetry. Almost every capability exists in four forms. File access is FileInputStream, FileOutputStream, FileReader, FileWriter. In-memory access is ByteArrayInputStream, ByteArrayOutputStream, StringReader, StringWriter. Pipe access is PipedInputStream, PipedOutputStream, PipedReader, PipedWriter. Learn one family and you have learned the others.

Wrapper classes break the pattern deliberately. BufferedInputStream, DataInputStream and ObjectInputStream are not sources at all — they are filters that take another stream and add a capability to it. They sit under FilterInputStream, which is the base class for exactly this purpose.

CONNECTION TO ANOTHER CONCEPT

Chapter 6 is entirely about those wrappers. The idea they implement — add a capability by wrapping, without changing the underlying source — is the decorator pattern, and it is why a single chain of objects can read a typed double efficiently from a file while the file stream itself knows nothing about doubles.

4.7The one rule about closing

Every stream holds an operating-system resource: a file handle, a pipe buffer, a socket. Those are finite. Failing to release them leaks them, and a long-running application will eventually fail to open anything at all.

Java gives you two ways to guarantee release, and both are used in BasinWatch.

// (a) try-with-resources — the preferred form
try (BufferedWriter writer = Files.newBufferedWriter(report, StandardCharsets.UTF_8)) {
    writer.write("BASINWATCH · SITUATION REPORT");
    writer.newLine();
    // ... more writes
}   // close() runs here, even if an exception was thrown

// (b) implementing AutoCloseable on a component that owns a stream
public final class OperationalJournal implements AutoCloseable {
    private final BufferedWriter writer;
    private int pendingLines;

    public OperationalJournal(Path path) throws IOException {
        writer = Files.newBufferedWriter(path, StandardCharsets.UTF_8,
                StandardOpenOption.CREATE, StandardOpenOption.APPEND);
    }

    @Override
    public synchronized void close() throws IOException {
        writer.flush();
        writer.close();
    }
}
from BasinWatch, io/ReportWriter.java and io/OperationalJournal.java — both release patterns.
CORE CONCEPT

Resources are released in reverse order of acquisition. In try (BufferedInputStream in = new BufferedInputStream(Files.newInputStream(p))) the buffered stream is closed first, which flushes it into the file stream, which is then closed. That order is what makes the last bytes reach the disk.

CHAPTER SUMMARY
  • A stream is an ordered, one-directional sequence of data, consumed or produced incrementally rather than all at once.
  • Every stream is described by three properties: direction, unit (byte or character), and source or destination.
  • Four abstract roots: InputStream, OutputStream, Reader, Writer.
  • Byte streams carry raw 8-bit units and preserve data exactly; character streams carry 16-bit characters through a charset and are correct for text.
  • read() returns int so that -1 can mark end of stream; readLine() returns null instead.
  • Stream failures are checked IOExceptions; EOFException is a subclass indicating a truncated read.
  • Streams are released by try-with-resources or by implementing AutoCloseable, in reverse order of acquisition.
KEY TERMS
  • Stream — an incremental, one-directional sequence of data.
  • Charset — the reversible mapping between characters and bytes, for example UTF-8.
  • Filter stream — a stream that wraps another stream and adds a capability.
  • try-with-resources — a statement that closes every declared resource automatically, in reverse order.
  • End of stream — the signal that no more data will arrive: -1 from read(), null from readLine().

5.1From a stream to an actual file

Chapter 4 described streams in the abstract. To make one real you attach it to a file, and that requires two different objects in modern Java: a Path that names the file, and a stream that reads or writes its contents.

IMPORTANT DISTINCTION

A File or Path is not the file's contents. It is a description of where the file is. You can ask it whether the file exists, what it is called, how large it is and when it was modified — all without opening it. Only when you create a stream do you touch the data. BasinWatch uses this distinction deliberately: it lists saves by inspecting metadata, and reads contents only when a save is actually restored.

5.4A complete read workflow

Reading has one extra consideration: you do not know how many lines there are, so the loop must be driven by the read itself.

import java.io.BufferedReader;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public class ReadWorkflow {
    public static void main(String[] args) throws IOException {
        Path source = Path.of("demo", "notes.txt");
        if (!Files.isRegularFile(source)) {
            throw new IOException("No such file: " + source.toAbsolutePath());
        }
        int lines = 0;
        try (BufferedReader reader =
                     Files.newBufferedReader(source, StandardCharsets.UTF_8)) {
            String line;
            while ((line = reader.readLine()) != null) {   // null marks end of stream
                lines++;
                System.out.println(lines + ": " + line);
            }
        }
        System.out.println("Read " + lines + " line(s)");
    }
}

5.6Flushing: when data actually reaches the disk

A buffered stream keeps data in memory until the buffer fills or you flush. This means that "the write succeeded" and "the bytes are on disk" are different statements.

BASINWATCH IN PRACTICE

The journal manages this explicitly, with a policy rather than a reflex. It flushes when twelve lines have accumulated, or immediately when the message is operationally significant:

public synchronized void append(ActivityEntry entry) throws IOException {
    writer.write(DateTimeFormatter.ISO_INSTANT.format(entry.at()));
    writer.write(" | ");
    writer.write(entry.category().replace('\n', ' '));
    writer.write(" | ");
    writer.write(entry.message().replace('\n', ' '));
    writer.newLine();
    pendingLines++;
    if (pendingLines >= 12 || entry.category().contains("WARNING")
            || entry.category().contains("COMPLETE")
            || entry.category().contains("ALLOCATED")) {
        writer.flush();
        pendingLines = 0;
    }
}
Listing 5.3 — from BasinWatch, io/OperationalJournal.java

This is a real engineering trade-off. Flushing every line would guarantee durability but cost a system call per line. Never flushing would be fast but could lose a burst of activity in a crash. Flushing on the important categories means that an allocation, a completion or a warning is on disk immediately, while routine readings can wait a few lines.

CONCEPT EXPLAINED FURTHER

The two replace('\n', ' ') calls are not cosmetic. An activity message could contain a newline — from an exception message, for example — and a newline inside a log line would break the file's one-line-per-entry structure. Replacing it with a space preserves the format without losing information.

IMPORTANT DISTINCTION

flush() and close() are not the same. flush() pushes buffered data to the operating system but leaves the stream usable. close() flushes and releases the file handle, after which any further write throws IOException. Calling close() twice is safe and has no additional effect.

CHAPTER 6

Buffering, Data Streams and Stream Wrappers

How a wrapper adds a capability without changing the source, why buffering changes performance by orders of magnitude, and how typed values are written to a binary file.

6.1The problem with one byte at a time

Every read() call on a raw file stream is a system call. The operating system has to leave user code, consult its file-system layer, copy a byte, and return. That overhead is roughly the same whether you asked for one byte or eight thousand.

So reading a megabyte one byte at a time means a million system calls to move data that would fit in 128 calls of 8 KB. The CPU spends its time in the kernel boundary rather than on your program. Buffering fixes this by adding an intermediate array.

CORE CONCEPT

A buffer is a memory array that sits between your code and the underlying resource. On the first read the buffer is filled with one large request; subsequent reads are served from memory until the buffer is exhausted, at which point it is refilled. Writing works in reverse: bytes accumulate in the buffer and are written out in one large operation when the buffer fills, when you flush, or when you close.

6.2Layering: the decorator pattern

The classes that add buffering, typing and object support are not sources. They take another stream in their constructor and wrap it. That single design choice is what makes stream code composable.

Read that diagram from the bottom up, because that is the direction data travels on a read. The file stream delivers raw bytes. The buffered stream collects them into an array so the file stream is called rarely. The data stream interprets the next four bytes as a double and the next four as an int. Each layer knows only the layer beneath it.

The same chain on a write goes the other way: your code calls writeDouble, the data stream converts the value to eight bytes, the buffered stream collects those bytes, and the file stream eventually writes them out.

BASINWATCH IN PRACTICE

BasinWatch's archive writer is exactly this chain, built in one statement:

            Files.newOutputStream(path, StandardOpenOption.CREATE, StandardOpenOption.APPEND)));
    if (fresh) {
        output.writeInt(MAGIC);
        output.writeInt(FORMAT_VERSION);
        output.flush();
    }
    return output;
}

Three layers, three capabilities: Files.newOutputStream talks to the file, BufferedOutputStream batches the bytes, and DataOutputStream converts typed values to bytes. The fresh test decides whether the header must be written — an archive that already contains data must not get a second header.

6.4Data streams: typed values in a binary file

A character stream can store the text "12.5". A data stream can store the number 12.5 — eight bytes in a defined format that any Java program can read back without parsing.

DEFINITION

DataInputStream / DataOutputStream — filter streams that read and write Java's primitive types and UTF-8 strings in a fixed binary format, independent of locale and of how the value would be printed.

Every data-stream write has exactly one matching read, and the order must be identical. A file written as writeInt then writeDouble must be read as readInt then readDouble. There is no self-describing metadata inside a data stream — the sequence of calls is the schema. Change the order in one place and every subsequent read returns garbage, usually without an exception.

COMMON MISTAKE

Reading a data stream in the wrong order is the classic silent corruption. Because every method simply consumes the next n bytes, a readDouble() where a readInt() was expected does not throw — it returns a perfectly valid but completely wrong number. The only defence is to keep the write order and the read order adjacent in the codebase and to version the format explicitly, which BasinWatch does with FORMAT_VERSION.

Four things in those listings are worth naming, because they are the difference between a toy binary format and a usable one.

A magic number identifies the file. The constant 0x42574152 spells "BWAR" in ASCII. If someone points the reader at a different file, the first read fails immediately with a clear message rather than producing nonsense.

A version number allows the format to change. When the layout gains a field, the version is incremented and the reader can decide what to do. Without it, an old reader would silently misinterpret a new file.

End of file is the terminator. There is no record count, so the loop reads until EOFException and treats that as the normal end. This is why the record must be written completely: a half-written record produces an EOFException in the middle of a record, which the reader cannot distinguish from a clean end unless it tracks how far it got.

The strings use writeUTF. Each string carries its own length, so there is no ambiguity about where one ends and the next begins. That is precisely what writeChars cannot offer.

CONNECTION TO ANOTHER CONCEPT

Compare this with Chapter 8's session snapshot, which stores whole objects rather than typed primitives. Both are binary, both are byte streams — but the data stream gives you a format you control field by field, while object serialization gives you a format the JDK controls and that you must actively secure. Neither is universally better; the archive chose control, the snapshot chose convenience plus validation.

CHAPTER 7

In-Memory and Piped Streams

Streams whose source is memory, and streams that connect two threads. This chapter covers byte-array streams, piped streams, and the producer–consumer pattern.

7.1Why a stream with no file?

Not every stream is attached to a device. Two important sources and destinations are entirely inside the program: a byte array in memory, and a pipe connecting two threads.

The in-memory case is useful because it lets you reuse the whole stream API for something that never touches a disk. Building a payload with DataOutputStream gives you the same typed writes as a file, and the result is a byte[] you can hand to a network call, a cache or a test assertion.

The piped case is useful because it solves a real problem: two threads that must exchange a stream of data without sharing a data structure.

7.2Byte-array streams

A ByteArrayOutputStream collects everything written to it in an internal growable array; toByteArray() hands you the contents. A ByteArrayInputStream reads from an array you already have.

import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.DataInputStream;

BasinWatch's archive code is written so that only the innermost source changes.

7.3Piped streams

A pipe is a matched pair: a writer at one end, a reader at the other, with a bounded buffer between them. What the writer writes, the reader reads, in order.

DEFINITION

Piped stream — a connected pair of streams, PipedWriter/PipedReader or PipedOutputStream/PipedInputStream, that transfers data from one thread to another through an internal buffer.

Three properties of that arrangement matter, and each is a design decision.

The pipe is the only shared object. The producer never sees the buffer, the queue or the model. The consumer never sees the producer. Each thread's dependencies are visible in its constructor.

The pipe is bounded, so it provides back-pressure. BasinWatch constructs it with an 8,192-character buffer. If the producer runs faster than the consumer, the producer blocks on write instead of filling memory. This is the same property a bounded queue has, obtained for free.

Both ends must be closed for the reader to finish cleanly. The writer closing is what turns the reader's next readLine() into a null, ending the loop. If the writer never closes, the reader waits forever.

COMMON MISTAKE

A pipe is not automatically thread-safe in the sense people assume. A PipedReader and its PipedWriter are intended to be used by different threads. Using both ends in one thread is a classic deadlock: the reader blocks waiting for data that only the same thread could write. If you need a stream in one thread, use a byte-array stream.

7.4The producer side

The producer is a thread with a loop, a cadence and a stop flag. Its job is to encode a value and write it as one line.

public final class SensorFeed extends Thread {
    private final Writer destination;
    private final List<String> zoneIds;
    private final SimulationSettings settings;
    private final AtomicLong tickSequence;
    private final Consumer<String> failureReporter;
    private volatile boolean running = true;

    @Override
    public void run() {
        Random random = new Random();
        try {
            while (running && !isInterrupted()) {
                long tick = tickSequence.incrementAndGet();
                for (String zoneId : zoneIds) {
                    SensorReading reading = new SensorReading(tick, stationId(zoneId), zoneId,
                            round1(random.nextDouble() * settings.rainfallMillimeters()),
                            round1(random.nextDouble() * settings.riseCentimeters()));
                    destination.write(reading.encode());
                    destination.write(System.lineSeparator());
                }
                destination.flush();
                Thread.sleep(settings.tickIntervalMillis());
            }
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();      // restore the flag and stop
        } catch (IOException ex) {
            failureReporter.accept("Sensor feed stopped: " + ex.getMessage());
        } finally {
            closeQuietly();
        }
    }
}
from BasinWatch, engine/SensorFeed.java — encode one line per observation, then flush.

Five details in that loop are worth studying, because each one is a concurrency decision.

running is volatile. It is written by one thread (the caller of requestStop()) and read by another (this loop). Without volatile, the reader could cache a stale value and never stop.

The loop checks both the flag and the interrupt. Either mechanism alone is enough, but checking both means a stop request works whether it arrives between iterations or during the sleep.

InterruptedException restores the flag. Catching the exception clears the thread's interrupt status, so Thread.currentThread().interrupt() puts it back. This is the correct handling and it is easy to get wrong.

The line separator is platform-independent at the source. Using System.lineSeparator() means the encoding matches what readLine() expects on the same machine.

The writer is closed in a finally block. That is what makes the consumer's loop terminate, even if the producer stopped because of an error.

7.5The consumer side

The consumer reads lines, validates them and passes accepted events onward. It is a Runnable rather than a thread, because the engine owns the thread.

public final class SensorIntake implements Runnable {
    private final BufferedReader source;
    private final EventBuffer buffer;
    private final Consumer<String> warningReporter;
    private final Consumer<String> statusReporter;

        }

7.6Wiring the pair, and shutting it down

Creating a connected pipe requires the writer to exist before the reader, and the reader's constructor to receive the writer. That ordering is why the engine builds both in one method.

public synchronized void closeEngine() {
    try {
        if (sensorFeed != null) {
            sensorFeed.requestStop();          // 1. stop producing
        }
        if (feedWriter != null) {
            feedWriter.close();                // 2. closing the writer ends readLine()
        }
        if (intakeThread != null) {
            intakeThread.join(2_000);          // 3. wait for the consumer to drain
        }
        eventBuffer.close();                   // 4. wake any waiting workers
        // ... archive drain, journal flush, final snapshot
    } catch (IOException | InterruptedException ex) {
        Thread.currentThread().interrupt();
    }
}
from BasinWatch, engine/BasinEngine.java — creation order and shutdown order are both deliberate.

The shutdown sequence is the part students most often get wrong, so it is worth stating as a rule. The four steps are ordered by dependency: you must stop the producer before closing the pipe, close the pipe before waiting for the consumer (otherwise the consumer blocks forever), and close the queue after the consumer has drained it (otherwise accepted events are lost).

Shutdown ordering, and what breaks if it is wrong
  1. Stop the producer. requestStop() sets the flag; the feed loop exits at the next check.
  2. Close the writer. This flushes any buffered characters into the pipe and signals end of stream.
  3. Join the intake thread. The consumer's readLine() now returns null, the loop ends, and the thread finishes. A bounded join with a timeout means shutdown cannot hang forever.
  4. Close the buffer. Waiting workers are woken by notifyAll and see the closed flag, so they exit instead of waiting for events that will never come.
  5. If you close the writer before stopping the producer: the producer throws IOException on its next write and reports a spurious failure.
  6. If you close the buffer before joining the consumer: events already read from the pipe are discarded, so the log and database lose the last few observations.
  7. If you never close the writer: the consumer blocks in readLine() forever and the application will not exit.

  • End of stream — in a pipe, the signal produced by closing the writer.
  • volatile — a field modifier guaranteeing that a write by one thread becomes visible to another.
  • Interrupt — a cooperative request for a thread to stop; it does not force termination.

CHAPTER 8

Serialization, Deserialization and Session Persistence

How objects are turned into bytes and back, why that is dangerous by default, and how a real application makes it safe.

8.1The problem: saving an object graph

A data stream can save a double because a double has a fixed size and layout. But what about an object? An object has fields of different types, may contain other objects, may contain collections of objects, and may have a class hierarchy. Writing it out field by field is tedious and breaks whenever a field is added.

Object serialization solves this by letting the runtime do the traversal. You declare that a class is serializable, and the JVM writes the object's class identity and its non-transient field values, recursing into any objects those fields reference.

DEFINITION

Serialization — the process of converting an object into a byte sequence that can be written to a stream and later reconstructed, preserving the object's class and field values.

DEFINITION

Deserialization — the reverse process: reading that byte sequence and reconstructing an object graph, including the classes it contains.

8.2How it works

Two classes do the work, and they are both filter streams, so they follow exactly the pattern from Chapter 6.

import java.io.*;

public class SerializeDemo {
    public static void main(String[] args) throws IOException, ClassNotFoundException {
        Path path = Path.of("demo", "sample.ser");

        // ---- serialization: object -> bytes -> file ----
        try (ObjectOutputStream out = new ObjectOutputStream(
                new BufferedOutputStream(Files.newOutputStream(path,
                        StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING)))) {
            out.writeObject(new Sample("MIL", 2.45, 12));
            out.flush();
        }

        // ---- deserialization: file -> bytes -> object ----
        try (ObjectInputStream in = new ObjectInputStream(
                new BufferedInputStream(Files.newInputStream(path)))) {
            Object restored = in.readObject();
            System.out.println("restored = " + restored);
        }
    }

    static final class Sample implements Serializable {
        private static final long serialVersionUID = 1L;
        private final String zone;
        private final double level;
        private final int residents;
        Sample(String zone, double level, int residents) {
            this.zone = zone; this.level = level; this.residents = residents;
        }
        @Override public String toString() {
            return zone + " " + level + " m / " + residents + " residents";
        }
    }
}

8.3The five facts that matter

1. A class must implement Serializable. It is a marker interface: it declares no methods. Its only purpose is to permit the runtime to write the object. Any class that does not implement it, and is not an ancestor, causes NotSerializableException at write time.

2. Fields must be serializable too, or marked transient. Serialization recurses, so every non-transient field must itself be serializable or a primitive. A Thread, an open Stream, a Connection — none of these can be serialized, and trying produces an exception naming the offending field.

3. transient excludes a field. A transient field is skipped entirely and, on deserialization, receives its default value: null, 0 or false. This is how you exclude a cache, a lock or a derived value.

4. static fields are not serialized. They belong to the class, not the object, so they are not part of the instance state being written.

5. The constructor is not called on deserialization. The object is allocated and its fields are set directly by the runtime. This is why the no-argument constructor that serialization conventionally requires need not do anything, and why validation placed in a constructor will not run when an object is restored.

CORE CONCEPT

Fact five is the one that surprises people, and it is the reason a real application cannot simply trust the objects it reads. If a constructor enforces "water level must be between 0 and 8", that rule is bypassed entirely by deserialization. BasinWatch therefore validates the restored state explicitly after reading it, rather than assuming the invariants held.

8.4serialVersionUID and version compatibility

Every serializable class has an identity that the stream records. If you declare it yourself, the compiler uses your value. If you do not, the compiler derives one from the class's structure — its name, its modifiers, its interfaces and every method and field signature.

8.5Why default serialization is unsafe

Deserialization reconstructs an object graph from bytes that may come from anywhere. The runtime will happily instantiate whatever classes the stream names. That is a security problem, not a theoretical one: a crafted stream can instantiate classes you never intended, and the "gadget chains" that made several widely reported vulnerabilities possible all relied on exactly this.

DEFINITION

Deserialization vulnerability — the risk that a malicious byte stream causes the runtime to instantiate and initialise classes of the attacker's choosing, because deserialization bypasses constructors and honours the class names in the stream.

There are four independent defences, and a robust implementation uses all of them rather than picking one.

8.6How BasinWatch saves and restores a session

The project's snapshot store is a careful implementation of the four defences, and reading it is the best way to see them in practice. It writes to a temporary file and then replaces the real file atomically, so a crash during a save cannot leave a half-written snapshot in place.

public final class SnapshotStore {
    static final int FORMAT_VERSION = 1;
    static final long MAX_SAVE_BYTES = 4L * 1024 * 1024;   // 4 MB is generous for this model

    public void save(Path target, SessionSnapshot snapshot) throws IOException {
        Files.createDirectories(target.toAbsolutePath().getParent());
        Path temporary = target.resolveSibling(target.getFileName() + ".tmp");
        try (ObjectOutputStream out = new ObjectOutputStream(new BufferedOutputStream(
                Files.newOutputStream(temporary, StandardOpenOption.CREATE,
                        StandardOpenOption.TRUNCATE_EXISTING)))) {
            out.writeInt(FORMAT_VERSION);      // written first, so a reader can check it early
            out.writeObject(snapshot);
            out.flush();
        }
        try {
            Files.move(temporary, target, StandardCopyOption.REPLACE_EXISTING,
                    StandardCopyOption.ATOMIC_MOVE);       // atomic replace
        } catch (AtomicMoveNotSupportedException ex) {
            Files.move(temporary, target, StandardCopyOption.REPLACE_EXISTING);
        }
    }
}
from BasinWatch, io/SnapshotStore.java — write to a temporary file, then move it into place.

Two things in the write path are deliberate. The version is written before the object, so a reader can reject an incompatible file without attempting to interpret it. And the save goes to name.bws.tmp first, with the real file replaced only when the write has succeeded. If the process dies mid-save, the previous good snapshot is still intact.

public SessionSnapshot load(Path source) throws IOException, ClassNotFoundException {
    if (!Files.isRegularFile(source)) {
        throw new IOException("Session save not found: " + source.toAbsolutePath());
    }
    if (Files.size(source) > MAX_SAVE_BYTES) {              // defence 1: bound the input
        throw new IOException("Session save is unexpectedly large: " + Files.size(source) + " bytes");
    }
    try (ObjectInputStream in = new ObjectInputStream(new BufferedInputStream(
            Files.newInputStream(source)))) {
        in.setObjectInputFilter(SnapshotStore::allowOnlySafeClasses);   // defence 2: filter classes
        int version = in.readInt();
        if (version != FORMAT_VERSION) {                    // defence 4: version check
            throw new IOException("Unsupported session format version: " + version);
        }
        Object payload = in.readObject();
        if (!(payload instanceof SessionSnapshot snapshot)) {
            throw new IOException("Session save does not contain a session snapshot.");
        }
        snapshot.validate();                                // defence 3: validate the domain state
        return snapshot;
    }
}

private static ObjectInputFilter.Status allowOnlySafeClasses(ObjectInputFilter.FilterInfo info) {
    Class<?> type = info.serialClass();
    if (type == null || type.isPrimitive()) {
        return ObjectInputFilter.Status.ALLOWED;
    }
    String name = type.getName();
    if (name.startsWith("com.basinwatch.") || name.startsWith("java.lang.")
            || name.startsWith("java.util.") || name.startsWith("java.time.")) {
        return ObjectInputFilter.Status.ALLOWED;
    }
    return ObjectInputFilter.Status.REJECTED;               // everything else is refused
}

Four file mechanisms, four different purposes. This chapter consolidates Part II into a verified case study of the project's file layer.

9.1The design question, stated properly

An application that needs to keep data could write everything to one file. BasinWatch uses four different file mechanisms, and the reason is that each answers a different question.

Table 9.1 — The four file artefacts and the question each one answers.
ArtefactThe question it answersMechanismWho reads it
operations.log“What has the application been doing?”Character stream, UTF-8, append-only, line per eventAn operator, or a text editor
sensors.bin“What exactly did the stations report?”Byte stream with data-stream typing, header plus fixed recordsThe program, during diagnosis

CORE CONCEPT

None of these four is interchangeable with the others, and that is the design lesson of Part II. A log cannot restore a session because it records events, not state. A snapshot cannot answer "what happened at 14:03" because it records only the present. An archive cannot be read by a person because it is binary. A report cannot be queried because it is prose. Choosing the format is choosing which questions the file will be able to answer.

Four properties make this file useful, and each was a decision.

The timestamp is ISO-8601 with a Z suffix. That is DateTimeFormatter.ISO_INSTANT, which sorts lexicographically in the same order as it sorts chronologically. A log that sorts correctly as text is a log you can grep.

The category is a separate field. Because it is delimited by " | ", an operator can filter for RISK or ALLOCATED with ordinary text tools.

Newlines inside a message are replaced. Chapter 5 covered this: it keeps one entry on one line, which is what makes the file greppable in the first place.

Flushing is category-aware. Routine observations can wait; warnings, completions and allocations are written through immediately, because those are the entries an investigation would want after a crash.

9.5The session snapshot

The snapshot is the only artefact that can bring the application back to where it was. It is written on request, and automatically on a clean shutdown, into last-session.bws.

IMPORTANT DISTINCTION

Why a separate SessionSnapshot rather than serializing BasinSnapshot directly? Three reasons, and all three matter. First, the domain types may contain things that cannot or should not be serialized. Second, the on-disk format should be a deliberate contract rather than an accident of the current field list — a DTO lets the model change without changing the file. Third, records and enums carry serialization constraints that plain final classes avoid. The DTO is a boundary object, and boundary objects should be explicit.

9.8Why not one file for everything

It is worth answering the obvious objection directly. Suppose you wrote everything to the log as text. You would then face four problems.

  1. Restoring state would mean replaying. To recover the model you would have to re-apply every event ever logged, in order, and hope the replay logic still matches the original.
  2. Numbers would lose precision. A double printed as text and parsed back may not be bit-identical, and any aggregation over thousands of readings would accumulate error.
  3. Diagnosis would mean parsing. A tool wanting "every reading for MIL above 20 mm" would have to parse the whole file rather than seek.
  4. One corrupt line would break everything. A truncated final line in an append-only log is normal after a crash; if that log were also the only save file, the session would be unrecoverable.

Conversely, if everything were one binary snapshot, you would lose the audit trail entirely. The four-mechanism design exists because the questions are genuinely different.

The log is an audit trail; the database is an index. Chapter 10 makes that distinction precise.

10.3Relational structure in one page

A relational database stores data in tables. A table has named columns with declared types and zero or more rows. A primary key uniquely identifies a row; a foreign key references a row in another table, which is how relationships are expressed.

Read that definition as a set of promises the database will enforce for you.

PRIMARY KEY AUTOINCREMENT gives every row a unique identity without the application inventing one. NOT NULL on every column means a missing value is rejected rather than silently stored as null. The types are declared, so rainfall_mm cannot hold the text "twelve".

The index is the important line. Without it, a query for one zone's recent readings must examine every row. With it, the database walks the index directly to the matching rows in the right order — which is exactly the query the interface makes.

10.5Where JDBC fits

Java cannot speak SQL to a database directly. There is no shared memory, no common protocol, and each database vendor has its own wire format. JDBC is the layer that bridges the gap.

DEFINITION

JDBC — the Java Database Connectivity API: a standard set of interfaces in java.sql that let Java code open a connection, send SQL, and read results without depending on a particular database product.

The key idea is that the application depends on interfaces, not on the database. Change from SQLite to PostgreSQL and the application code does not change — only the driver on the classpath and the connection URL do.

CONNECTION TO ANOTHER CONCEPT

10.6Why SQLite specifically

SQLite is a complete relational database implemented as a library, not as a server. The database is a single file on disk, and the "connection" is a handle to that file. For an offline desktop application that is an ideal fit.

11.1The two halves of JDBC

JDBC is deliberately split in two. One half is fixed and shipped with Java: the interfaces in java.sql. The other half is supplied by whoever makes the database: the driver, which implements those interfaces for one specific product.

CORE CONCEPT

This is the single most important structural fact about JDBC, and it is worth stating plainly: every method you call on a Connection is code you have never read. The interface is in the JDK; the implementation is in the driver jar. That is why changing the driver can change behaviour, and why exact exception messages differ between databases.

11.2What the driver actually does

A driver has four responsibilities.

  1. Recognise its own URLs. Given jdbc:sqlite:data/basinwatch.db, the SQLite driver accepts it and other drivers decline.
  2. Open a connection. For SQLite that means opening the file; for PostgreSQL it means a TCP connection, a handshake and authentication.
  3. Translate calls into the database's protocol. A PreparedStatement.setDouble(3, 12.4) becomes whatever bytes that database expects.
  4. Translate results back. A result row becomes a ResultSet positioned on that row, with typed getters.

11.6How BasinWatch manages connections

The project wraps connection handling in one small class, so no repository has to know the URL.

public final class DatabaseManager {
    private static final String DRIVER_CLASS = "org.sqlite.JDBC";
    private final String url;

    public DatabaseManager(Path databaseFile) {
        this.url = "jdbc:sqlite:" + databaseFile.toAbsolutePath();
    }

    public Connection openConnection() throws SQLException {
        Connection connection = DriverManager.getConnection(url);
        connection.setAutoCommit(true);            // each statement commits on its own
        return connection;
    }

    public boolean isAvailable() {
        try (Connection connection = openConnection()) {
            return connection.isValid(2);          // two-second validity check
        } catch (SQLException ex) {
            return false;                          // absence is reported, not thrown
        }
    }

    public String url() {
        return url;
    }
}
from BasinWatch, db/DatabaseManager.java — one place that knows the URL.

Three decisions in that class shape everything downstream.

The URL is built once, in the constructor. No other class contains the string "jdbc:sqlite:".

isAvailable returns a boolean rather than throwing. This is what makes the database optional. The application asks "is history available?" and handles both answers, instead of being forced to handle an exception merely to find out.

Autocommit is set explicitly. It is the default, but stating it documents the decision — and Chapter 13 shows the one place where it is deliberately turned off.

CONNECTION TO ANOTHER CONCEPT

Notice that isAvailable catches SQLException and converts it into false. That is an exception-translation decision, and Chapter 14 explains why the rest of the application depends on it: an unavailable database must not prevent the application from running.

12.3Why PreparedStatement matters: SQL injection

This is the most important practical lesson in the chapter, and the demonstration is short.

// ---- DANGEROUS: values concatenated into the SQL text ----
String zone = userInput;                                  // e.g.  MIL' OR '1'='1
String sql = "SELECT * FROM sensor_readings WHERE zone_id = &#x27;" + zone + "'";
Statement statement = connection.createStatement();
ResultSet rs = statement.executeQuery(sql);

// the database actually receives:
//   SELECT * FROM sensor_readings WHERE zone_id = 'MIL' OR '1'='1'
// the OR clause is now part of the statement, so EVERY row matches.

// ---- SAFE: the value is bound, never parsed as SQL ----
String safeSql = "SELECT * FROM sensor_readings WHERE zone_id = ?";
try (PreparedStatement ps = connection.prepareStatement(safeSql)) {
    ps.setString(1, userInput);                           // bound as a VALUE
    try (ResultSet rs2 = ps.executeQuery()) {
        // the database receives a plan for the fixed text,
        // plus one parameter whose value is MIL' OR '1'='1 -- a literal string
    }
}
illustrative — the injection vulnerability and its fix

The difference is not about escaping characters. With a PreparedStatement, the SQL text is sent to the database and parsed before the parameter values are supplied. The parser has already decided what is a statement and what is a value, so no value can become part of the statement's structure. Quoting and escaping become irrelevant because the value never enters the parser's input.

IMPORTANT DISTINCTION

Concatenating values into SQL is unsafe even when you escape them yourself. Manual escaping has to handle quote characters, backslashes, multi-byte encodings and database-specific syntax, and getting it subtly wrong is easy. Binding parameters removes the problem entirely rather than mitigating it. BasinWatch uses PreparedStatement at every site, including the statements with no parameters.

Placeholders are numbered from one, and each needs a typed setter matching the column's type.

12.6Reading a ResultSet

A result set is a cursor. It starts before the first row, so the loop must advance before reading.

public List<DatabaseHistoryEntry> loadHistory(Connection connection, int limit)
        throws SQLException {
    String sql = """
            SELECT occurred_at, event_type, zone_id, detail
              FROM operational_events
             ORDER BY occurred_at DESC
             LIMIT ?
            """;
    ArrayList<DatabaseHistoryEntry> entries = new ArrayList<>();
    try (PreparedStatement statement = connection.prepareStatement(sql)) {
        statement.setInt(1, limit);
        try (ResultSet rows = statement.executeQuery()) {
            while (rows.next()) {                          // advance, then read
                entries.add(new DatabaseHistoryEntry(
                        DatabaseHistoryType.valueOf(rows.getString("event_type")),
                        rows.getString("zone_id"),
                        rows.getString("detail"),
                        Instant.parse(rows.getString("occurred_at"))));
            }
        }
    }
    return List.copyOf(entries);
}
from BasinWatch, db/OperationalEventRepository.java — the canonical read loop.

Four habits in that method are the whole of result-set handling.

The loop is while (rows.next()). next() moves the cursor and returns false when there are no more rows. A do-while would be wrong, because the cursor starts before the first row.

Columns are read by name. rows.getString("event_type") is clearer than rows.getString(2) and survives a change to the select list. The trade-off is a small lookup cost, which is irrelevant here.

Each row is converted into a domain object inside the loop. The method returns List<DatabaseHistoryEntry>, not a ResultSet. That is essential: a result set is tied to its statement and its connection, and once they close it is unusable. Converting immediately means the caller receives ordinary values.

List.copyOf makes the result immutable. The same discipline as every other boundary in the project.

COMMON MISTAKE

Returning a ResultSet from a method that also closes the connection. The caller receives an object that looks usable and fails with SQLException: ResultSet closed on the first next(). The rule is that a result set never outlives the block that created it — map rows into your own objects before leaving.

12.8The complete lifecycle, in order

Everything in this chapter reduces to one sequence. Learn it as a sequence, because examiners and reviewers both ask for it.

The eight steps of a parameterized query
  1. Obtain a connection. DriverManager.getConnection(url), inside try-with-resources.
  2. Prepare the statement. connection.prepareStatement(sql) sends the SQL text to the database, which parses and plans it once.
  3. Bind every parameter. One typed setter per placeholder, indices 1 to n, no gaps.
  4. Execute. executeQuery() for a read, executeUpdate() for a write.
  5. Consume the result. For a query, loop with while (rows.next()) and map each row into a domain object. For an update, check the returned row count.
  6. Close the result set. Handled by its own try-with-resources block.
  7. Close the statement. Handled by the statement's try-with-resources block.
  8. Close the connection. Handled by the outermost try-with-resources block — and this is where a transaction would be committed or rolled back.
CONNECTION TO ANOTHER CONCEPT

Step eight is where Chapter 13 begins. Everything above happens inside a transaction, whether you think about it or not: in autocommit mode each statement is its own transaction, and turning autocommit off lets several statements share one.

EXAM TIP

If asked to "write the code to insert a row safely", the marks are distributed roughly as follows: using PreparedStatement rather than concatenation; binding every parameter with the correct type and 1-based index; using executeUpdate; and closing all three resources. Mentioning try-with-resources explicitly is usually worth a mark on its own.

  • PreparedStatement is the default choice: safer, pre-parsed, and reusable.
  • Concatenating values into SQL permits injection; binding parameters makes the value unable to become part of the statement.

  • SQL injection — an attack in which user input becomes part of a statement's structure.

CHAPTER 13

Database Transactions and Reliable Persistence

Transaction boundaries, commit and rollback, and why several related changes must succeed or fail together.

13.1The problem: a half-finished operation

Consider what a dispatch actually involves. A mission row must be created. Several resource counts must be decremented. An event must be recorded for the audit trail. These are three separate statements against three separate tables.

If the first succeeds and the second fails, the database now claims a mission is running with resources that were never deducted. That is not a small inconsistency: the resource board will be wrong for the rest of the session, and the history will not explain why.

DEFINITION

Transaction — a group of database operations treated as a single unit: either every operation in the group takes effect, or none of them does.

13.2The four guarantees

Transactions are described by four properties, known by the acronym ACID. Each is worth understanding in concrete terms rather than as a slogan.

Table 13.1 — The ACID properties and what each means here.
PropertyMeansIn this project
AtomicityAll operations take effect, or none doA dispatch writes a mission, deducts resources and logs an event — or writes nothing
ConsistencyThe database moves from one valid state to anotherNOT NULL and type constraints hold at commit time
IsolationConcurrent transactions do not see each other's partial workThe database work runs on a single thread, so there is one writer
DurabilityOnce committed, the change survives a crashSQLite flushes the committed transaction to the database file

13.3Controlling a transaction in JDBC

By default a connection is in autocommit mode: each statement is committed immediately as its own transaction. Turning autocommit off gives you control.

connection.setAutoCommit(false);        // begin: nothing commits until you say so
try {
    // ... statement 1
    // ... statement 2
    // ... statement 3
    connection.commit();                // all three become visible together
} catch (SQLException ex) {
    connection.rollback();              // undo everything since setAutoCommit(false)
    throw ex;
} finally {
    connection.setAutoCommit(true);     // restore the default for the next caller
}
illustrative — the standard transaction skeleton
CORE CONCEPT

Notice the shape: turn autocommit off, do the work in a try, commit at the end of the try, roll back in the catch, and restore autocommit in a finally. The finally matters when the connection comes from a pool and will be reused by someone who does not expect an open transaction.

COMMON MISTAKE

Forgetting to roll back, or forgetting to restore autocommit. Both leave the connection in an unexpected state. A missing rollback means a later commit could persist work that was supposed to be discarded; a missing restore means the next user of a pooled connection accidentally joins your transaction. BasinWatch avoids the first problem by rolling back in the catch block and the second by closing the connection afterwards rather than pooling it.

13.4How BasinWatch records a dispatch

The dispatch path is the project's one genuine multi-statement operation, and it is where the transaction is used.

public void recordDispatch(ResponseMission mission, ZoneSnapshot zone,
                         Map<ResourceType, Integer> allocation, Instant timestamp) {
    enqueue(() -> {
        try (Connection connection = database.openConnection()) {
            connection.setAutoCommit(false);               // begin the transaction
            try {
                missions.insert(connection, mission, timestamp);        // 1. the mission row
                for (Map.Entry<ResourceType, Integer> entry : allocation.entrySet()) {
                    resourceUsage.insert(connection, mission.id(), entry.getKey(),
                            entry.getValue(), timestamp);               // 2. one row per resource
                }
                operationalEvents.insert(connection, timestamp, "DISPATCH", zone.id(),
                        mission.type().label() + " allocated to " + zone.name());  // 3. the audit event
                connection.commit();                       // all three take effect together
            } catch (SQLException ex) {
                connection.rollback();                     // none of them take effect
                throw ex;
            }
        } catch (SQLException ex) {
            statusReporter.accept("Could not record dispatch: " + ex.getMessage());
        }
    });
}
from BasinWatch, db/DatabaseService.java — one transaction, three kinds of write.
VISUAL WALKTHROUGH

Follow the three numbered writes in that method. If the third throws, the rollback undoes the first two — so the database never contains a mission with no audit event, or resource deductions with no mission. That is what atomicity buys, and it is why the transaction boundary is drawn around all three rather than around each one.

13.5Why the writes share one connection

This is the detail that most often goes wrong in student implementations, and it explains the package-private overloads from Chapter 2.

        throws SQLException {

    }

from BasinWatch, db/MissionRepository.java — the two overloads and why both exist.
IMPORTANT DISTINCTION

A transaction belongs to a connection, not to a statement. Calling commit() on one connection has no effect on work done on another. So if three repositories each opened their own connection, three separate transactions would exist and atomicity would be lost entirely — the code would look correct and silently not be. Passing one connection through every write is the mechanism that makes the transaction real.

13.6Isolation, and why it is simple here

Isolation is the property that governs what one transaction can see of another's uncommitted work. Real systems offer several isolation levels, trading consistency against concurrency, and reasoning about them is one of the harder parts of database engineering.

BasinWatch sidesteps the whole problem in one design decision: all database work runs on a single dedicated thread. There is exactly one writer, so there is never a second transaction to interfere.

private void enqueue(DatabaseOperation operation) {
    if (!available) {
        return;                                  // database disabled: silently do nothing
    }
    try {
        executor.submit(() -> {
            try {
                operation.run();
            } catch (SQLException ex) {
                statusReporter.accept("Database operation failed: " + ex.getMessage());
            } catch (RuntimeException ex) {
                statusReporter.accept("Unexpected database error: " + ex);
            }
        });
    } catch (RejectedExecutionException ex) {
        statusReporter.accept("Database queue is full; operation dropped.");
    }
}
from BasinWatch, db/DatabaseService.java — one single-threaded executor is the whole concurrency policy.

That method is worth reading closely, because it is where several chapters meet.

The executor is single-threaded. Every database operation runs one after another on "basin-database". No two transactions are ever concurrent, so no isolation anomaly is possible and no locking policy is needed.

An unavailable database is a no-op, not an error. The early return means every call site can invoke recordSensor or recordDispatch without checking availability first. The optional subsystem is optional at the call site too.

Failures are reported, not thrown. A database failure cannot propagate into the event processing path, because the work happens on a different thread. It is reported through the status listener and the application continues.

A full queue drops the operation rather than blocking. RejectedExecutionException is caught and reported. For an optional history feature, dropping a record is better than stalling the sensor pipeline.

CONNECTION TO ANOTHER CONCEPT

Compare this with the resource allocator in Chapter 3. That used a synchronized block to make an in-memory reservation atomic. Here the database provides atomicity through a transaction. Two different mechanisms, one shared goal: never let a partially complete change be observable.

EXAM TIP

A likely question is "give an example from your project where a transaction is needed, and explain what would go wrong without it." The dispatch path is the ideal answer: without a transaction, a failure after the mission insert would leave a running mission with resources that were never deducted, so the resource board would be permanently wrong and the audit trail would not explain it. Naming the three writes and the failure point is what makes the answer convincing.

14.4Tracing a reading from the sensor to the table

This is the central trace of the chapter. Follow one observation all the way to a stored row.

One accepted observation, from pipe to table
  1. The feed encodes it. SensorFeed builds a SensorReading and writes reading.encode() plus a line separator into the PipedWriter.
  2. The intake parses it. SensorIntake reads the line and calls SensorReading.parse(line), which validates the field count and ranges.
  3. The intake queues it. eventBuffer.put(event) hands it to the workers; the call blocks if the buffer is full.
  4. A worker processes it. One of the three ResponseWorker threads takes the event and calls model.process(event), which applies the reading to the zone and returns activity messages.
  5. The worker fans out. The engine appends to the journal, submits to the archive worker, and — if the reading was accepted and changed the zone — calls database.recordSensor(...).
  6. The service queues it. recordSensor calls enqueue, which submits a lambda to the single-threaded executor and returns immediately.
  7. The worker thread runs it. The lambda opens a connection, and SensorReadingRepository.insert prepares the nine-placeholder statement and binds every value.
  8. SQLite executes it. The driver sends the statement and the bound values; the database inserts the row and commits it, because autocommit is on.
  9. If it was a risk escalation, a second insert follows. An operational_events row is written with the type RISK ESCALATION.
  10. A failure is reported, not thrown. Any SQLException is caught by enqueue's lambda and passed to the status listener, which posts it to the interface.

14.6Why the database is optional

The final question about this layer is the most important one: why does the application work without it?

Four mechanisms together produce that isolation, and each was a decision.

Availability is a boolean, checked once. DatabaseManager.isAvailable catches the exception and returns false, so the rest of the code tests a value rather than handling a failure.

Every write is a queued lambda. Because the work happens on another thread, an exception there cannot propagate into the caller's stack.

The queue wrapper catches everything. enqueue catches both SQLException and RuntimeException and routes them to the status listener.

A read on an unavailable database returns an empty list. The interface's code path is identical in both cases, so no branch is needed at the call site.

CORE CONCEPT

This is the design pattern worth taking away from Part III, and it generalises well beyond databases: an optional subsystem should be detectable, isolated, and silent-on-absence. Detectable through a boolean or a capability query. Isolated by running on its own thread so failures cannot propagate. Silent-on-absence by returning a sensible empty result rather than raising an error the caller must anticipate.

EXAM TIP

If asked "what happens if the database is unavailable?", the complete answer has four parts: the application still starts, because availability is checked rather than assumed; the history panel shows an empty list and a status message; all writes become no-ops; and the file layer is entirely unaffected, so the log, archive, snapshot and reports are still produced. Answering with only the first part is the usual mistake.

15.1What makes a program event-driven?

A procedural program runs from top to bottom: it reads input, computes, prints output, and exits. A graphical program does none of that. It starts, builds a window, and then waits. Everything that happens afterwards happens because something triggered it — a click, a key press, a timer, a window being resized.

The structure that makes this work is a loop that never ends and a set of callbacks that the loop invokes. In Swing, that loop lives on a dedicated thread called the event-dispatch thread, and every listener you register runs on it.

DEFINITION

Event-driven programming — a style in which the program declares handlers for events and then waits, letting the framework invoke the appropriate handler when each event occurs, rather than controlling the sequence of execution itself.

CORE CONCEPT

Three consequences follow from the event-driven model, and they explain almost every Swing rule in this chapter.

  1. You do not control the order of execution. The user does.
  2. All event handling and all painting happen on one thread. So any long operation inside a handler freezes the entire interface.
  3. Components must be updated from that thread. Touching a Swing component from another thread is unsafe.

15.6The lecture-note login application

The lecture notes contain a Swing login screen. It is a small program, but it demonstrates most of the fundamentals at once, so it is worth walking through carefully.

import javax.swing.*;
import java.awt.*;

public class LoginApplication {
    private final JFrame frame = new JFrame("Login");
    private final JTextField usernameField = new JTextField(16);
    private final JPasswordField passwordField = new JPasswordField(16);
    private final JButton loginButton = new JButton("Login");
    private final JLabel statusLabel = new JLabel("Enter your credentials", SwingConstants.CENTER);

    public LoginApplication() {
        JPanel form = new JPanel(new GridLayout(2, 2, 8, 8));
        form.add(new JLabel("Username:"));
        form.add(usernameField);
        form.add(new JLabel("Password:"));
        form.add(passwordField);

        JPanel content = new JPanel(new BorderLayout(8, 8));
        content.setBorder(BorderFactory.createEmptyBorder(12, 12, 12, 12));
        content.add(form, BorderLayout.CENTER);
        content.add(loginButton, BorderLayout.SOUTH);
        content.add(statusLabel, BorderLayout.NORTH);

        loginButton.addActionListener(event -> attemptLogin());

        frame.setContentPane(content);
        frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        frame.pack();
        frame.setLocationRelativeTo(null);          // centre on screen
        frame.setVisible(true);
    }

    private void attemptLogin() {
        String username = usernameField.getText().trim();
        char[] password = passwordField.getPassword();
        if (username.isEmpty() || password.length == 0) {
            statusLabel.setText("Both fields are required.");
            return;
        }
        if ("admin".equals(username) && "secret".equals(new String(password))) {
            statusLabel.setText("Welcome, " + username + ".");
        } else {
            statusLabel.setText("Incorrect username or password.");
            passwordField.setText("");              // clear the password on failure
        }
    }

    public static void main(String[] args) {
        SwingUtilities.invokeLater(LoginApplication::new);
    }
}
lecture-note style — the Swing login application, annotated

15.7What the login program actually does

It builds a component tree. A GridLayout panel holds two label and field pairs. That panel sits in the centre of a border layout, with the button below and the status label above. Nothing is positioned by coordinates.

It registers one listener. The button's action listener calls attemptLogin(). That is the only connection between the user and the logic.

It validates before comparing. An empty username or password produces a specific message, which is more useful than "incorrect credentials". This is the same validate-at-the-boundary habit as SensorReading.parse.

It reads the password as a char[], not a String. That is not stylistic. JPasswordField.getPassword() returns a character array precisely so that the caller can overwrite it when finished. A String is immutable and its contents may persist in memory until garbage collection, so a password held in a String is readable from a memory dump for longer than necessary.

It clears the password on failure. A small detail with a real security purpose: the credential is not left on screen for someone walking past.

It starts on the event-dispatch thread. main does nothing but schedule the constructor with SwingUtilities.invokeLater. Every component is therefore created on the EDT, which is the rule.

TECHNICAL CLARIFICATION

This program checks a hard-coded credential in the client. That is fine for a demonstration of Swing mechanics and unacceptable for a real system, for three reasons. The password appears in the compiled code. There is no hashing, so anyone reading the class file learns the credential. And any check performed in the user interface can be bypassed by anyone who can run different code. A real login compares a hash of the submitted password against a stored hash, and it does so on a server the user does not control. The lecture example is a UI exercise, not a security pattern — and saying so is part of understanding it.

COMMON MISTAKE

Calling new LoginApplication() directly from main instead of through SwingUtilities.invokeLater. It often appears to work, because the components happen to be created before the window is shown. But Swing's internals assume single-threaded access, and creating components off the EDT can produce intermittent, hard-to-reproduce failures in layout or painting. The fix is one line, and it is not optional.

15.8Custom painting

When a component must draw something Swing does not provide — a schematic map, for instance — you override paintComponent.

@Override
protected void paintComponent(Graphics graphics) {
    super.paintComponent(graphics);              // always first: clears and paints the background
    Graphics2D g = (Graphics2D) graphics;
    g.setRenderingHint(RenderingHints.KEY_ANTIALIASING,
            RenderingHints.VALUE_ANTIALIAS_ON);
    for (ZoneSnapshot zone : snapshot.zones()) {
        Point centre = positionOf(zone.id());
        g.setColor(colourFor(zone.risk()));
        g.fillOval(centre.x - RADIUS, centre.y - RADIUS, RADIUS * 2, RADIUS * 2);
        g.setColor(Color.WHITE);
        g.drawString(zone.id(), centre.x - 12, centre.y + 4);
    }
}
from BasinWatch, app/BasinMapPanel.java — custom painting, condensed.

Three rules govern paintComponent, and all three matter.

Call super.paintComponent first. It clears the component's area. Without it, previous frames are never erased and the drawing smears as the component is repainted.

Never perform slow work inside it. Painting runs on the event-dispatch thread, and it runs whenever the window is uncovered, resized or asked to repaint. Reading a file or running a query here would freeze the interface repeatedly.

Never call repaint() from inside it. That requests another paint, which requests another repaint, producing an unresponsive loop. To change what is drawn, change the data and then call repaint() from elsewhere.

CONNECTION TO ANOTHER CONCEPT

This is why the engine publishes immutable snapshots. The paint method reads snapshot on the event-dispatch thread while workers may be mutating the model on other threads. Because the snapshot is an immutable copy, the paint method sees a consistent picture with no locking at all.

EXAM TIP

A very common question asks why a long-running task in an ActionListener freezes the interface. The complete answer: the handler runs on the event-dispatch thread, and that same thread is responsible for delivering subsequent events and performing all painting. While the handler is busy, neither can happen, so the window appears frozen even though the application is running. The fix is to move the work to a background thread and post the result back — the subject of Chapter 16.

CHAPTER SUMMARY
  • Swing is event-driven: the program declares handlers and then waits for the framework to call them.
  • Components fall into top-level containers, intermediate containers and simple components.
  • Layout is managed by a layout manager per container; BorderLayout for the frame with nested layouts inside it is the standard composition.
  • Events are dispatched to registered listeners, and all event handling runs on the event-dispatch thread.
  • A listener can be a named class, an anonymous class, a lambda or a method reference; lambdas work because the listener interfaces are functional.
  • The lecture-note login application validates input, reads the password as a char array, clears it on failure, and starts on the EDT.
  • Custom painting goes in paintComponent, must call super first, must be fast, and must never call repaint.
  • A hard-coded credential check in a UI is a demonstration of mechanics, not a security design.
KEY TERMS
  • Event-dispatch thread (EDT) — the single thread that runs Swing event handling and painting.
  • Listener — an object registered to be notified when a particular event occurs.
  • Functional interface — an interface with exactly one abstract method, so a lambda can implement it.
  • Layout manager — the object that decides where a container's children are placed.
  • paintComponent — the method overridden to draw a custom component.
CHAPTER 16

Connecting Application Logic, JDBC and Swing

From a click to a command, through a background thread and a database query, back to a visible table — and the one thread rule that governs all of it.

16.1The problem this chapter solves

Chapter 15 established that all Swing work happens on the event-dispatch thread. Chapter 12 established that a database query is a blocking operation. Put those two facts together and you have a conflict: running the query in a listener freezes the window.

This chapter is about resolving that conflict without introducing a worse one. The solution has four parts, and each is a rule rather than a trick.

CORE CONCEPT
  1. A listener does not do the work. It asks the engine for an operation and returns.
  2. Slow work happens on a background thread. The engine's executors own those threads.
  3. The result is delivered as a future. A callback runs when the value arrives.
  4. The callback posts to the EDT before touching any component. Every time, without exception.

16.2Step one: the listener asks, and returns

BasinWatch's listeners are short by design. Each one translates a user gesture into an engine call and nothing else.

startButton.addActionListener(event -> {
    if (engine.isRunning()) {
        engine.pause();
    } else {
        engine.start();

    refreshControlStates();
});

stormButton.addActionListener(event -> engine.injectStorm(1.35, 0.42));
reportButton.addActionListener(event -> engine.exportReport());
saveButton.addActionListener(event -> chooseAndSave());
refreshHistoryButton.addActionListener(event -> historyPanel.reload());

None of those handlers opens a file, runs a query or waits for anything. That is the point. A listener that returns quickly cannot freeze the interface, and the method names read like the operations the user is actually performing.

16.4Step three: the result arrives as a future

An operation that produces a result returns a CompletableFuture. The caller attaches a callback and carries on.

public CompletableFuture<Path> exportReport() {
    return CompletableFuture.supplyAsync(() -> {
        try {
            BasinSnapshot snapshot = model.snapshot();
            Path report = ReportWriter.write(AppPaths.reportsDirectory(), snapshot);
            publishStatus("Report written to " + report.getFileName());
            return report;
        } catch (IOException ex) {
            publishStatus("Could not write the report: " + ex.getMessage());
            throw new CompletionException(ex);
        }
    }, controlExecutor);
}
from BasinWatch, engine/BasinEngine.java — the work is supplied to an executor; the caller gets a future.

Three properties of that method are the pattern.

The work is a supplier submitted to a named executor. supplyAsync(..., controlExecutor) runs on "basin-control", not on the caller's thread and not on the common pool.

Failures are converted. IOException is checked, and a supplier cannot throw it, so it is wrapped in CompletionException. The future then completes exceptionally, and any whenComplete callback can inspect the cause.

The status is published from the worker thread. publishStatus is called inside the supplier, so it runs on the control thread. The listener that receives it must hop to the EDT — which brings us to step four.

16.5Step four: the callback posts to the EDT

This is the rule that everything else depends on.

// Registering a listener: the engine may call it from ANY thread
engine.addStatusListener(message ->
        SwingUtilities.invokeLater(() -> statusLabel.setText(message)));

// Attaching a callback to a future: it runs on the completing thread
engine.loadHistory(200).whenComplete((entries, failure) ->
        SwingUtilities.invokeLater(() -> {
            if (failure != null) {
                historyStatus.setText("History unavailable: " + failure.getMessage());
                return;
            }
            historyTableModel.setEntries(entries);
            historyStatus.setText(entries.size() + " entries loaded.");
        }));
from BasinWatch, app/MainFrame.java and app/DatabaseHistoryPanel.java — every callback hops to the EDT.
CORE CONCEPT

Notice that SwingUtilities.invokeLater appears in both places, and in exactly the same position: wrapping the entire body that touches a component. That is the rule stated precisely. It is not enough to call it somewhere in the method — the component access must be inside the lambda that is posted.

IMPORTANT DISTINCTION

invokeLater and invokeAndWait are different, and one of them is dangerous. invokeLater queues the runnable on the EDT and returns immediately — the calling thread continues. invokeAndWait queues it and blocks until the EDT has run it, which is a deadlock if you call it from the EDT. BasinWatch uses invokeLater exclusively.

16.6The complete path, from click to table cell

Now the two halves of the book can be joined. Here is the whole path for one user action: pressing "Refresh" in the history panel.

From a button press to a populated table
  1. The user clicks Refresh. The operating system delivers a mouse event to the window.
  2. The EDT dispatches it. Swing calls the ActionListener registered on that button.
  3. The listener calls one method. historyPanel.reload() — and returns immediately.
  4. reload asks the engine for a future. engine.loadHistory(200) returns a CompletableFuture at once.
  5. The engine checks availability. If the database is unavailable it returns an already-completed future holding an empty list, so no error path is needed.
  6. The engine enqueues the query. A lambda is submitted to the single-threaded database executor.
  7. The database thread opens a connection. DatabaseManager.openConnection() on basin-database.
  8. The repository prepares and binds. A PreparedStatement with one placeholder for the limit.
  9. SQLite executes. The query is planned and the matching rows are returned in descending time order.
  10. The rows are mapped to objects. Each row becomes a DatabaseHistoryEntry, inside the result-set loop.
  11. The future completes on the database thread. future.complete(entries) runs the whenComplete callback on that same thread.
  12. The callback posts to the EDT. SwingUtilities.invokeLater queues a runnable.
  13. The EDT runs the runnable. The table model's entries are replaced and the status label is updated.
  14. Swing repaints. The table asks its model for the new row count and redraws only the visible cells.
VISUAL WALKTHROUGH

Follow the thread changes in that list: EDT, then database thread, then EDT again. Steps one to four are EDT. Steps five to eleven are the database thread. Steps twelve to fourteen are EDT again. The two invokeLater boundaries are the only places the two threads touch.

16.7Why the table model matters

A JTable does not store data. It asks a TableModel for it, and the model is where the application's data lives.

final class HistoryTableModel extends AbstractTableModel {
    private static final String[] COLUMNS = {"Time", "Type", "Zone", "Detail"};
    private List<DatabaseHistoryEntry> entries = List.of();

    void setEntries(List<DatabaseHistoryEntry> entries) {
        this.entries = List.copyOf(entries);       // defensive copy, immutable
        fireTableDataChanged();                    // tell the table to ask again
    }

    @Override public int getRowCount() { return entries.size(); }
    @Override public int getColumnCount() { return COLUMNS.length; }
    @Override public String getColumnName(int column) { return COLUMNS[column]; }

    @Override public Object getValueAt(int row, int column) {
        DatabaseHistoryEntry entry = entries.get(row);
        return switch (column) {
            case 0 -> entry.at();
            case 1 -> entry.type();
            case 2 -> entry.zoneId() == null ? "\u2014" : entry.zoneId();
            default -> entry.detail();
        };
    }
}
from BasinWatch, app/DatabaseHistoryPanel.java — a table model over immutable rows.

Three things in that class are worth noting.

The model holds the data, and the table renders it. Replacing the entries and calling fireTableDataChanged() is what makes the table update. Without the notification, the table would keep displaying stale rows, because it has no way to know the model changed.

setEntries takes an immutable copy. The list came from the database thread; copying it removes any possibility of concurrent modification while the EDT is reading.

The nullable zone is handled in the view. operational_events.zone_id is nullable by design, and the model renders null as a dash rather than the text "null".

CONNECTION TO ANOTHER CONCEPT

Compare this with the login application in Chapter 15. That program put its logic directly in a private method of the frame class. BasinWatch puts the logic in the engine and gives the panel only a table model. Both are Swing programs; the difference is that one is a demonstration of mechanics and the other is an application with a persistence layer behind it. Neither is wrong — but the second is what you need when the data comes from a database.

RELATED TECHNIQUE — NOT USED IN BASINWATCH

Some applications use SwingWorker instead of futures. It is a JDK class with doInBackground() on a worker thread and process() and done() on the EDT, and it solves the same problem. BasinWatch does not use it, for one reason: the engine must work without a user interface, so its operations cannot depend on a Swing type. Returning CompletableFuture keeps the engine independent of Swing, and the interface chooses how to consume the result. If you are asked which is better, the honest answer is that SwingWorker is more convenient inside a UI and CompletableFuture is more flexible outside one.

EXAM TIP

The highest-value question in this part is "trace the path of a user action that reads from the database." Answer it as a thread journey, not a class list: the EDT handles the click, the call returns a future immediately, the query runs on the database thread, the future completes there, and the callback posts back to the EDT to update the model. Mention invokeLater explicitly, and mention that the interface never blocks.

CHAPTER SUMMARY
  • A listener must return quickly, so it asks the engine for an operation rather than performing one.
  • The engine owns several executors and named threads, each with a specific job.
  • Operations that produce a result return CompletableFutures, so the caller never blocks.
  • Any code touching a Swing component must be wrapped in SwingUtilities.invokeLater, including callbacks from futures.
  • invokeLater queues and returns; invokeAndWait blocks and can deadlock if called from the EDT.
  • A complete click-to-table path crosses the EDT, the database thread, and the EDT again.
  • A JTable renders whatever its TableModel provides, and the model must call fireTableDataChanged to trigger an update.
  • The engine returns futures rather than using SwingWorker, so that it remains independent of Swing.
KEY TERMS
  • invokeLater — queueing a runnable to run on the event-dispatch thread, without waiting.
  • CompletionException — the wrapper used when a checked exception must be thrown from an asynchronous supplier.
  • TableModel — the object supplying data to a JTable.
  • fireTableDataChanged — the notification that tells a table its model's contents have changed.
  • Thread confinement — the rule that a particular object may only be accessed from one thread; Swing components are confined to the EDT.

17.1The problem a build tool solves

Compiling a single file is easy: javac Hello.java. Compiling a project is not. A build tool automates four things: resolving dependencies, compiling, testing, and packaging. Maven is one such tool, and it is the one BasinWatch uses.

17.5Where the JDBC driver comes from

Chapter 11 asked why the driver is on the classpath and answered "a Maven dependency". Here is the mechanism.

How the SQLite driver reaches the running program
  1. Declared. pom.xml names org.xerial:sqlite-jdbc:3.50.3.0.
  2. Resolved. Maven downloads the jar from a repository into the local cache, typically ~/.m2/repository.
  3. Added to the compile classpath. The compiler can now resolve any driver-specific types referenced in the source.
  4. Added to the runtime classpath. When the program runs, the jar is on the class path, so org.sqlite.JDBC is loadable.
  5. Discovered automatically. The jar contains META-INF/services/java.sql.Driver, so the JDK registers the driver without any code.
  6. Selected by URL. DriverManager.getConnection("jdbc:sqlite:…") asks each registered driver whether it accepts the URL; the SQLite driver says yes.
COMMON MISTAKE

Forgetting that the driver must be on the runtime classpath, not just the compile classpath. This is the classic cause of SQLException: No suitable driver found in a program that compiles perfectly. The dependency is present when the compiler runs and absent when the program runs — usually because the jar was built without it, which is the next section's subject.

17.6Packaging a runnable jar

A plain jar contains only your own compiled classes. Run it and the driver is missing. Maven's shade plugin solves this by producing an "uber jar": your classes plus the dependency classes, merged into one file.

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-shade-plugin</artifactId>
    <version>3.6.0</version>
    <executions>
        <execution>
            <phase>package</phase>
            <goals><goal>shade</goal></goals>
            <configuration>
                <createDependencyReducedPom>false</createDependencyReducedPom>
                <transformers>
                    <!-- CRITICAL: merge META-INF/services files from every jar -->
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer"/>
                    <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">
                        <mainClass>com.basinwatch.app.BasinWatchApp</mainClass>
                    </transformer>
                </transformers>
            </configuration>
        </execution>
    </executions>
</plugin>
from BasinWatch, pom.xml — the shade plugin and the transformer that matters.
CORE CONCEPT

The ServicesResourceTransformer is not optional. Without it, the shading process would keep only one META-INF/services/java.sql.Driver file and discard the others. The merged jar would then contain the SQLite driver's classes but no registration, and the application would fail with "No suitable driver found" — even though the driver is physically inside the jar. This is one of the most confusing failures in Java packaging, and the transformer is the fix.

The ManifestResourceTransformer sets Main-Class in the jar's manifest, which is what makes java -jar basinwatch-1.0.0.jar start the application instead of printing an error.

17.7Why this matters to the rest of the book

The build file is not administrative overhead. It is the answer to three questions the other chapters raise.

  • Why does the JDBC code compile? Because java.sql is in the JDK and the driver is on the compile classpath.
  • Why does the JDBC code run? Because the driver is on the runtime classpath and registers itself through a service file.
  • Why does the application start with one command? Because the shade plugin merged everything into one jar and set Main-Class.

Remove any one of those and the application stops working, even though no Java source changed. That is the lesson of this chapter: the build is part of the program.

19.1The repetition in raw JDBC

Look back at any repository method in Chapter 12 and count the lines that are about the query rather than about the resource handling.

public List<DatabaseHistoryEntry> loadRecent(int limit) throws SQLException {
    String sql = "SELECT ... FROM operational_events ORDER BY occurred_at DESC LIMIT ?";
    ArrayList<DatabaseHistoryEntry> entries = new ArrayList<>();
    try (Connection connection = database.openConnection()) {                 // boilerplate
        try (PreparedStatement statement = connection.prepareStatement(sql)) { // boilerplate
            statement.setInt(1, limit);                                       // the actual work
            try (ResultSet rows = statement.executeQuery()) {                 // boilerplate
                while (rows.next()) {                                         // boilerplate
                    entries.add(new DatabaseHistoryEntry(                     // the actual work
                            DatabaseHistoryType.valueOf(rows.getString("event_type")),
                            rows.getString("zone_id"),
                            rows.getString("detail"),
                            Instant.parse(rows.getString("occurred_at"))));
                }
            }
        }
    }
    return List.copyOf(entries);

from BasinWatch, db/OperationalEventRepository.java — three lines of intent inside ten lines of resource handling.

The structure is identical in every method: open a connection, prepare a statement, bind parameters, execute, iterate, close everything. Only the SQL and the row mapping change. That is the definition of code that wants to be abstracted.

CORE CONCEPT

Repetition like this is not merely ugly — it is a source of bugs. Every place that must remember to close a connection is a place that might forget. Every place that must bind parameters in the right order is a place that might get the order wrong. Raw JDBC in BasinWatch is safe because it is written carefully in a handful of repository classes; in a larger codebase, the same pattern repeated two hundred times would not stay safe.

19.2What Spring JdbcTemplate does

Spring's JdbcTemplate is a thin wrapper over the JDBC interfaces you already know. It performs exactly the steps in that method, and asks you to supply only the two things that vary: the SQL, and the code that turns a row into an object.

// ---- the same query, with JdbcTemplate ----

           + "FROM operational_events ORDER BY occurred_at DESC LIMIT ?";

List<DatabaseHistoryEntry> entries = jdbcTemplate.query(sql,
        (rows, rowNumber) -> new DatabaseHistoryEntry(
                DatabaseHistoryType.valueOf(rows.getString("event_type")),
                rows.getString("zone_id"),
                rows.getString("detail"),
                Instant.parse(rows.getString("occurred_at"))),
        limit);
lecture-note style — the same query expressed with Spring JdbcTemplate

20.2Scenario A: an observation, fully traced

This is the system's heartbeat. Nothing is clicked; the application produces its own data.

Scenario A — from the feed loop to a coloured zone on the map
  1. 1. The feed loop wakes. SensorFeed.run is in its timed loop on basin-sensor-feed. It increments the shared tick counter and begins a new interval.
  2. 2. Six readings are generated. For each of the six zones, a SensorReading is constructed with randomised rainfall and rise values within the configured bounds. The compact constructor validates the ranges as it is built.
  3. 3. Each reading is encoded and written. reading.encode() produces a pipe-delimited line such as READ|214|MIL-ST-2|MIL|12.400|3.100, which is written into the PipedWriter along with a line separator.
  4. 4. The pipe transfers and applies back-pressure. Characters move into the pipe's 8,192-character buffer. If intake has fallen behind and the buffer is full, the feed's write blocks here — the producer waits rather than overrunning memory.
  5. 5. Intake reads a line. On basin-sensor-intake, SensorIntake.run is blocked in source.readLine(). It wakes, receives the line, and returns it without the terminator.
  6. 6. The record is parsed and validated. SensorReading.parse splits on the pipe character and checks that there are exactly six fields beginning with READ. A malformed line is reported and skipped; the loop continues.
  7. 7. The event is queued. eventBuffer.put(event) adds it to the bounded deque. If the buffer is full, this call waits on the monitor; if it is closed, the method returns false and intake stops.
  8. 8. A worker takes it. One of the three ResponseWorker threads is waiting in eventBuffer.take(). It wakes, removes the event, and calls model.process(event).
  9. 9. The model applies it. applyReading finds the zone, calls BasinZone.apply(reading), and — crucially — receives false if the reading is stale. The risk level is recomputed from the new water level.
  10. 10. Escalation is detected. The new risk rank is compared with the previous one. If it increased, the activity message is prefixed with “Risk increased:” and a boolean is prepared for the database.
  11. 11. Activity is recorded and the snapshot is published. An ActivityEntry is added to the model's ring buffer, and model.snapshot() produces a new immutable BasinSnapshot.
  12. 12. The listener chain fires. BasinEngine calls every snapshot listener on the worker thread. Each listener's first action is SwingUtilities.invokeLater.
  13. 13. The EDT updates the interface. The map panel's snapshot field is replaced and repaint() is requested; the activity list and labels are updated. The zone's circle changes colour.
  14. 14. Persistence runs in parallel. The engine appends each activity message to the journal, submits the reading to the archive worker, and — only if the model changed — calls database.recordSensor(...).
  15. 15. The database thread writes. On basin-database, the repository prepares the nine-placeholder insert, binds every value, and executes it. If the risk escalated, a second row is written to operational_events.

    return;
}}

One boolean, decided in the domain, determines whether three separate persistence mechanisms write anything at all. That is what "the model is the source of truth" means in practice.

20.3Scenario B: a dispatch, and its transaction

This scenario starts with a person and ends with a changed resource board. It is also the only scenario that needs a database transaction.

Scenario B — from a dispatch click to a changed resource board
  1. 1. The operator selects a mission type and a zone, then clicks Dispatch. Two combo boxes and a button, all on the EDT.
  2. 2. The listener calls the engine. engine.dispatch(zoneId, missionType) — one call, returning immediately.
  3. 3. The engine submits the work. The request is submitted to basin-control and the caller receives a CompletableFuture.
  4. 4. The control thread reserves resources. ResourceAllocator.tryReserve(requirements) runs under the allocator's monitor: it checks every requirement, and only if all are satisfied does it decrement any of them.
  5. 5. A failed reservation stops here. If any resource is short, the method returns false, no state changes, and the future completes with a message the interface displays. Nothing is persisted, because nothing happened.
  6. 6. A successful reservation creates a mission. BasinModel constructs a ResponseMission with an identifier, a start tick and a completion tick derived from the mission type's duration.
  7. 7. The model publishes a new snapshot. The resource board now shows the deduction and the mission list shows the new operation. The listener chain posts both to the EDT.
  8. 8. Persistence begins. The engine appends an ALLOCATED entry to the journal and calls database.recordDispatch(...).
  9. 9. The database transaction opens. On basin-database, a connection is obtained and setAutoCommit(false) is called.
  10. 10. Three writes execute on that one connection. The mission row, one resource-usage row per required resource, and an audit event — all through package-private repository overloads that accept the shared connection.
  11. 11. The transaction commits. All three rows become visible together, or none of them does.
  12. 12. A failure rolls back. If any of the three throws, rollback() discards all of them, and the status listener reports the failure to the interface.
  13. 13. Completion is scheduled. In the model, the mission's completion tick is in the future. When the tick arrives, a later pulse completes the mission, releases the resources, and records a second transaction.
VISUAL WALKTHROUGH

Notice step four and step eleven are the same idea implemented twice. Step four makes an in-memory change atomic using a monitor; step eleven makes a database change atomic using a transaction. Both exist to prevent a partially completed change from being observable. Chapter 13 makes this comparison explicitly.

COMMON MISTAKE

A common wrong design puts the resource reservation after the database write. Then a failed reservation leaves a mission row claiming resources that were never deducted, and the history contradicts the live state. The order matters: reserve first, because the in-memory reservation is the decision, and the database records the decision.

20.4Scenario C: save, exit, and restore

This scenario is the only one whose result is visible on a later run, and it is the reason the snapshot format is versioned and validated.

Scenario C — from a save click to a restored basin on the next launch
  1. 1. The operator clicks Save. On the EDT, the listener opens a file chooser and obtains a target path.
  2. 2. The listener calls the engine. engine.save(target), returning a future.
  3. 3. The control thread takes a snapshot. model.snapshot() produces an immutable BasinSnapshot while holding the model's monitor, so the copy is consistent.
  4. 4. The snapshot is converted to a DTO. SessionSnapshot.from(snapshot) copies zones, resources, missions and recent activity into serializable plain classes.
  5. 5. A temporary file is written. SnapshotStore.save opens name.bws.tmp, writes the format version, then serializes the DTO.
  6. 6. The temporary file is moved into place. Files.move(..., ATOMIC_MOVE) replaces the real file in one step, so an interrupted save cannot corrupt an existing snapshot.
  7. 7. The status is reported. The future completes with the path, and the callback posts the message to the EDT.
  8. 8. Later, the application exits cleanly. closeEngine() stops the feed, closes the pipe, joins intake, drains the archive queue, flushes the journal, and writes last-session.bws automatically.
  9. 9. On the next launch, the engine checks for a restore point. It looks for last-session.bws in the saves directory.
  10. 10. Four gates are applied on load. The file size is bounded, an ObjectInputFilter approves only com.basinwatch, java.lang, java.util and java.time classes, the format version is compared, and the DTO is validated.
  11. 11. The model is rebuilt. Zones are restored with their water levels, the resource allocator is refilled, missions are reinstated with their remaining durations, and the activity ring buffer is repopulated.
  12. 12. The interface shows the restored state. The map, the resource board, the mission list and the activity timeline all reflect the saved session, and the tick counter resumes.
VISUAL WALKTHROUGH

Count the differences between the save path and the restore path. Saving is straightforward: copy, convert, write, move. Restoring is defensive: four gates before a single value is trusted. That asymmetry is deliberate and it is the single most important thing to understand about serialization in an application — writing is your own data, reading is unverified input.

20.5Scenario D: a history read

This scenario writes nothing. It is the shortest of the four, and it is the one that most directly connects JDBC to Swing.

Scenario D — from a Refresh click to a populated table
  1. 1. The operator clicks Refresh. Delivered to the EDT and dispatched to the button's listener.
  2. 2. The listener calls historyPanel.reload() and returns. Nothing blocks.
  3. 3. The panel asks the engine. engine.loadHistory(200) returns a future immediately.
  4. 4. Availability is checked. If the database is unavailable, an already-completed future holding an empty list is returned and steps five to eight are skipped.
  5. 5. The query is enqueued. A lambda is submitted to basin-database.
  6. 6. The repository prepares and binds. One placeholder for the limit, bound with setInt(1, limit).
  7. 7. SQLite executes and returns rows. The index on operational_events serves the descending time order.
  8. 8. Rows are mapped and the future completes. Each row becomes a DatabaseHistoryEntry; future.complete(entries) runs the callback on the database thread.
  9. 9. The callback posts to the EDT. SwingUtilities.invokeLater.
  10. 10. The table model is updated. setEntries(entries) copies the list and calls fireTableDataChanged().
  11. 11. The table repaints. It asks the model for the row count and redraws the visible rows.

20.7The dependency graph

Finally, the static picture: who depends on whom. Dependencies point one way, and that direction is what makes the layers testable and replaceable.

Three properties of that graph are worth naming.

The domain is at the bottom and depends on nothing. No file, no database, no Swing. That is why the model can be tested in a unit test with no setup at all, and why the same model could be driven by a different interface.

There are no cycles. Nothing the engine depends on depends on the engine. A cycle would make the layers impossible to test in isolation and impossible to replace.

The interface is at the top and depends on the engine, not the reverse. The engine has no import of javax.swing anywhere, which is what allows the whole application to run headless in a test.

21.2Guided walkthrough: following one class completely

Take SensorIntake. It is a small class — a single run method — but it sits at the junction of streams, threads, validation and queueing, so it is the ideal subject for the exercise.

public final class SensorIntake implements Runnable {
    private final BufferedReader source;
    private final EventBuffer buffer;
    private final Consumer<String> warningReporter;
    private final Consumer<String> statusReporter;

    public SensorIntake(BufferedReader source, EventBuffer buffer,
                        Consumer<String> warningReporter, Consumer<String> statusReporter) {
        this.source = source;
        this.buffer = buffer;
        this.warningReporter = warningReporter;
        this.statusReporter = statusReporter;
    }

    @Override
    public void run() {
        statusReporter.accept("Sensor intake online");
        try (source) {
            String line;
            while ((line = source.readLine()) != null) {
                BasinEvent event;
                try {
                    if (line.startsWith("PULSE|")) {
                        event = new SimulationPulse(Long.parseLong(line.substring(6)));
                    } else {
                        event = SensorReading.parse(line);
                    }
                } catch (IllegalArgumentException ex) {
                    warningReporter.accept("Discarded malformed sensor record: " + ex.getMessage());
                    continue;
                }
                if (!buffer.put(event)) {
                    warningReporter.accept("Event buffer closed; intake stopping.");
                    break;
                }
            }
        } catch (IOException ex) {
            warningReporter.accept("Sensor intake ended with an I/O error: " + ex.getMessage());
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();
        } finally {
            statusReporter.accept("Sensor intake offline");
        }
    }
}
from BasinWatch, engine/SensorIntake.java — the complete class, unedited.

Now apply the eight questions to it.

1. Why is this class needed?

Because reading and validating the observation stream is a distinct job with its own failure modes. It blocks on input, it must tolerate malformed data without stopping, and it must hand off to a queue that can be full. Putting that in SensorFeed would make the producer responsible for the consumer's timing; putting it in the workers would make every worker re-validate the same stream. As its own task, it can be reasoned about — and tested — alone.

2. How does it communicate with other classes?

Through four constructor arguments, each a narrow contract. A BufferedReader (a stream), an EventBuffer (a queue), and two Consumer<String> callbacks (events). It has no reference to the feed, the model, the engine or any interface class. That is why it can be tested by handing it a StringReader and a fresh buffer.

3. Which data does it receive?

Lines of text, one per event. Each line is either a pipe-delimited observation beginning with READ|, or a pulse beginning with PULSE|. It receives nothing else — no objects, no configuration, no state.

4. Does it use a stream, an event, a method call, or a database query?

All three of the first, and none of the last. A stream supplies the characters. A method call performs the parse, which validates. An event — a callback — reports warnings and status, and the queue hand-off is a fourth mechanism, condition waiting. There is no database interaction at all, which is correct: persistence is a decision for the engine, made after the model has processed the event.

5. How does its result affect the application?

Indirectly and only through the queue. For every accepted line it places one event in the buffer; a worker then takes it. For every rejected line it produces a warning and continues. It never returns a value, because it is a long-running task rather than a function — its effect is the stream of events it delivers.

6. What survives application shutdown?

Nothing that this class owns. The buffer's contents are drained and processed before shutdown; the pipe is closed; the reader is closed by try-with-resources. The durable record is created by the engine — a journal line, an archive record and possibly a database row — none of which this class touches. That separation is deliberate.

7. What happens if the relevant operation fails?

Three distinct outcomes, and the differences are the design.

  • A malformed line produces a warning and the loop continues. One bad record cannot stop the stream.
  • An IOException ends the loop and reports. The channel is broken; there is nothing left to read.
  • A closed buffer makes put return false, so intake reports and stops cleanly rather than waiting forever for a consumer that will never come.

8. Which design alternative is taught in the lecture notes?

Reading from a file with FileReader and a BufferedReader in a main method. That is the same read loop with a different source and no threading. The lecture version demonstrates the stream API; this version demonstrates what changes when the source is another thread and the consumer is concurrent — which is why the try-with-resources, the two failure categories and the closed-buffer check all matter.

A complete write is create, open, write, flush, close; a complete read is check, open with an explicit charset, loop on readLine() != null, close. flush() pushes data onward; close() flushes and releases.
6A buffer turns many small operations into few large ones. Wrapper classes add one capability each by taking another stream in their constructor. readLine() exists only on BufferedReader. Data streams write primitives in a fixed order that is the schema, so the read order must match exactly; a usable binary format has a magic number, a version and self-describing strings.
7Byte-array streams use the whole stream API with no device. A pipe is a matched writer/reader pair with a bounded buffer, intended for two threads; it provides back-pressure and a natural end-of-stream signal. Shutdown order is stop the producer, close the writer, join the consumer, close the queue.
8Serialization writes an object graph; deserialization reconstructs it without calling constructors. transient and static fields are skipped; an explicit serialVersionUID prevents unrelated recompiles from invalidating saves. Because constructors are bypassed, a reader needs four defences: bound the size, filter the classes, check the version, validate the result. BasinWatch writes to a temporary file and moves it into place.
9Four file mechanisms answer four questions: the log records what happened, the archive records exact measurements, the snapshot restores state, the report communicates. All paths derive from AppPaths. None of the four can substitute for another, because the format determines which questions the file can answer.
10Data lives in memory, in files, or in a database; the decisive difference is selective access through indexes. BasinWatch uses all three because different questions need different mechanisms. A table declares columns, types and constraints; an index makes a query fast; JDBC is the interface layer that lets Java talk to any database.
11JDBC splits into fixed interfaces in java.sql and a vendor driver that implements them. A driver recognises URLs, opens connections, translates calls and translates results back. There are four driver types; the pure-Java thin driver is the modern default. BasinWatch builds its URL in one place and reports availability as a boolean.
12A query involves a Connection, a Statement and possibly a ResultSet, all closed. PreparedStatement is the default: safer against injection, pre-parsed and reusable. Placeholders are 1-based and each needs a typed setter. executeQuery returns rows, executeUpdate returns a count. Map rows into your own objects inside the loop.
13A transaction groups operations so all take effect or none do; the ACID properties are atomicity, consistency, isolation and durability. JDBC is in autocommit mode by default; setAutoCommit(false) begins a transaction you control. A transaction belongs to a connection, so every statement in it must share that connection. BasinWatch records a dispatch in one transaction, and runs all database work on one thread so isolation anomalies cannot arise.
14Four classes form the database layer: connection management, schema creation, service coordination, and per-table SQL. Four tables carry readings, missions, resource usage and events, each with a timestamp. Schema creation is idempotent. The database is optional because availability is a boolean, writes are queued on their own thread, and reads on an unavailable database return an empty list.
15Swing is event-driven: handlers are declared and the framework calls them. Components are containers or simple components, arranged by layout managers. All event handling and painting run on the event-dispatch thread, which is why a slow handler freezes the window. The lecture-note login application validates input, reads the password as a char array and starts on the EDT; its hard-coded credential is a UI exercise, not a security design.
16A listener asks the engine and returns; slow work runs on a background thread; the result arrives as a future; and the callback posts to the EDT before touching any component. A complete click-to-table path crosses the EDT, the database thread and the EDT again. A JTable renders whatever its TableModel supplies, and the model must fire a change event.
17A build tool resolves dependencies, compiles, tests and packages. Maven identifies libraries by groupId, artifactId and version. BasinWatch has exactly one dependency. The driver reaches the runtime classpath as a Maven dependency and registers itself through a service file, which the shade plugin's ServicesResourceTransformer must preserve in the uber jar.
18XML is a tree of elements, attributes and text; a document is well-formed if it follows the syntax and valid if it conforms to a schema. A namespace URI is an identifier, not an address. Annotations are metadata whose retention policy decides whether a framework can read them at runtime. A JavaBean's conventions exist so a framework can instantiate and populate it reflectively; BasinWatch wires by hand instead.
19Raw JDBC forces the same resource handling into every method; JdbcTemplate performs it for you and asks only for SQL and a RowMapper. A DataSource supplies connections; DriverManagerDataSource does not pool and is for teaching and tests. JdbcTemplate is built on the same java.sql interfaces, so it removes repetition rather than JDBC. BasinWatch uses raw JDBC only.
20Four scenarios take genuinely different routes: an observation crosses the pipe and fans out to three persistence mechanisms; a dispatch is the only transactional path; a save-and-restore is defensive on the way in; a history read writes nothing. The dependency graph is acyclic, with the domain at the bottom and the interface at the top.
21Eight questions explain any class: purpose, communication, data received, mechanism, effect, survival, failure, and the lecture alternative. Every syllabus concept has a home in the project, and the three most defensible design alternatives are raw JDBC versus JdbcTemplate, files versus a database, and hand wiring versus a dependency-injection framework.
VIVA AND THEORY

Viva and Theory Questions

Fifty questions with answers, grouped from definitions through mechanisms to integration. The last group is the one that separates understanding from memorisation.

V.1Definitions and distinctions

Q1. What is a stream?
A one-directional, ordered sequence of data with a source or a destination, consumed or produced incrementally rather than all at once. The incrementality is the point: it lets you handle data larger than memory, and data that has no end yet.
Q2. State the difference between a byte stream and a character stream.
A byte stream carries 8-bit units and applies no interpretation, so it preserves data exactly. A character stream carries 16-bit characters and converts them through a charset, so it is correct for text a human will read. Using a character stream on binary data corrupts it, because byte sequences invalid in the charset are replaced.
Q3. Why does read() return an int rather than a byte?
Because the end of a stream needs a marker distinct from every legal data value. All 256 byte values are legal data, so widening the return type to int makes room for -1 to mean end of stream.
Q4. What is the difference between flush() and close()?
flush() pushes buffered data to the destination and leaves the stream usable. close() flushes and then releases the underlying resource; further writes after closing throw. Calling close() twice is safe.
Q5. What is a filter stream?
A stream that wraps another stream, taking it as a constructor argument, and adds one capability — buffering, typed reads, object serialization or character decoding. It is the decorator pattern applied to I/O, and it is what makes stream chains composable.
Q6. Define serialization and deserialization.
Serialization converts an object into a byte sequence containing its class identity and its non-transient field values, recursing into referenced objects. Deserialization reverses the process, reconstructing the object graph.
Q7. What do transient and static mean for serialization?
Neither is written to the stream. A transient field is skipped deliberately and restores to its default value; a static field belongs to the class rather than the instance, so it is not instance state and is not serialized.
Q8. What is serialVersionUID for?
It is the explicit version identity of a serializable class. Without it, the compiler derives one from the class's structure, so adding a method or a field can change it and make previously saved files unreadable with InvalidClassException. Declaring it makes compatibility deliberate.
Q9. What is a JavaBean, and how does it differ from a POJO?
A JavaBean is a POJO that follows conventions — a public no-argument constructor, private fields, public get/set accessors and usually Serializable — so a framework can create and populate it by reflection. Every JavaBean is a POJO; not every POJO is a JavaBean. A record can never be a JavaBean, because it has no no-argument constructor and no setters.
Q10. What is JDBC?
The Java Database Connectivity API: a set of interfaces in java.sql plus a driver-registration mechanism, letting Java code open connections, send SQL and read results without depending on a particular database product.
Q11. What is a primary key?
The column or columns that uniquely identify each row in a table. It prevents duplicate identities and is the target of references from other tables.
Q12. What is an index and why does it matter?
An auxiliary structure that lets the database find rows by particular columns without examining every row. It is the reason a selective query is cheap, and it is the main capability a database has that a plain file does not.
Q13. What is a transaction?
A group of database operations treated as one unit: either all of them take effect or none does. It is what prevents a partially completed change from being visible.
Q14. What do the ACID properties mean?
Atomicity: all or nothing. Consistency: the database moves between valid states, honouring its constraints. Isolation: concurrent transactions do not see each other's partial work. Durability: a committed change survives a failure.
Q15. What is the event-dispatch thread?
The single thread on which Swing performs event handling and painting. All component access must happen there, which is why a long-running handler freezes the interface and why callbacks from other threads must post their work to it.

V.2Mechanisms and code

Q16. Why does an application need both file-based logs and a database?
Because they answer different questions. A log records what happened, in order, and is readable with a text editor but must be scanned to be queried. A database stores structured rows that can be filtered, ordered and aggregated cheaply through indexes. The log is an audit trail; the database is an index over the same events.
Q17. What is the role of a JDBC driver?
Four things: recognise its own URLs, open a connection to the database, translate JDBC calls into the database's own protocol, and translate results back into ResultSet rows. Everything you call on a Connection is implemented by the driver, not by the JDK.
Q18. Which JDBC driver type does BasinWatch use, and why does that matter?
A type 4 thin driver, org.xerial:sqlite-jdbc. It is pure Java, so it needs no native library and no middleware — just a jar on the classpath. That is why the project's entire database configuration is one Maven dependency and one URL string.
Q19. How does PreparedStatement bind values, and why is that safe?
Placeholders written as ? are numbered from one, and each is filled by a typed setter such as setDouble(4, value). The SQL text is sent to the database and parsed before any value is supplied, so the parser has already decided what is a statement and what is a value. No value can therefore become part of the statement's structure, which is what defeats SQL injection.
Q20. What is the difference between executeQuery() and executeUpdate()?
executeQuery() runs a statement that produces rows and returns a ResultSet. executeUpdate() runs a statement that changes rows and returns the number of rows affected as an int.
Q21. Why must a result set be consumed inside the block that created it?
Because it is tied to its statement and its connection, and both are closed at the end of that block. Returning a ResultSet from a method that closes its connection produces an object that fails on the first next(). The fix is to map each row into your own object inside the loop.
Q22. How does a character stream differ from a byte stream in terms of the data it can represent?
Neither represents more data — both are sequences of units. The difference is interpretation: a byte stream preserves exact 8-bit values with no mapping, while a character stream applies a charset, so the same character may occupy one or several bytes on disk. Character streams are therefore lossless for text and destructive for binary data.
Q23. How does a piped stream relate to multithreading?
A pipe is a matched writer/reader pair intended for two different threads: one writes characters, the other reads them, and the pipe's bounded buffer transfers between them. It gives a one-directional contract with back-pressure and a natural end-of-stream signal when the writer closes. Using both ends in one thread is a deadlock, because the reader waits for data only that same thread could write.
Q24. What is a condition wait, and what are the four rules for writing one correctly?
A condition wait is wait() used to pause a thread until a predicate becomes true. The four rules: wait inside a loop that re-tests the predicate, because a woken thread is not guaranteed its condition now holds; hold the object's monitor, since wait() requires it; use notifyAll() rather than notify(), because waiters may have different predicates; and release the monitor while waiting, which wait() does and sleep() does not.
Q25. Why does BasinWatch use a pipe between the feed and the intake rather than a shared list?
Because the pipe is a much narrower contract. A shared list would give both threads access to every element and to the list's own methods, so a bug in either could corrupt it. The pipe gives each thread one operation — write a character sequence, read a character sequence — and provides back-pressure for free, since the writer blocks when the buffer is full.
Q26. What is the difference between writeUTF and writeChars?
writeUTF writes a two-byte length followed by modified UTF-8 bytes, so the string is self-describing and can be read back without knowing its length. writeChars writes two bytes per character with no length prefix, so the reader must already know how many characters to read.
Q27. Why does a data stream require the read order to match the write order?
Because the format contains no field metadata: the sequence of calls is the schema. A readDouble() where a readInt() was written does not throw — it consumes eight bytes that were never a double and returns a plausible but wrong value. Versioning the format explicitly is the defence.
Q28. What four defences does BasinWatch apply when restoring a session?
Bound the input size before opening the stream; install an ObjectInputFilter that approves only the project's own packages and a small set of JDK packages; check the format version written in the header; and validate the restored domain state, because deserialization bypasses constructors.
Q29. Why is the session snapshot written to a temporary file and then moved?
So that an interrupted save cannot corrupt an existing snapshot. The temporary file is written completely, then moved into place with ATOMIC_MOVE, which replaces the target in one step. A crash mid-save leaves the previous good file intact and an orphaned temporary file.
Q30. Why does DatabaseManager.isAvailable return a boolean rather than throwing?
Because the database is optional. Returning a boolean lets every caller test a value rather than handling an exception to discover availability, and it lets a read return an empty list on an unavailable database so the interface's code path is identical either way.

V.3Integration and architecture

Q31. How do database results reach a GUI?
In four steps. A listener on the event-dispatch thread asks the engine for an operation and returns immediately with a CompletableFuture. The query runs on the database thread. The future completes there, running its callback on that same thread. The callback wraps its component access in SwingUtilities.invokeLater, so the table model is updated on the event-dispatch thread.
Q32. Why does Spring JdbcTemplate not eliminate the need for JDBC itself?
Because it is built on JDBC. It obtains connections from a DataSource, creates PreparedStatements, binds parameters, iterates ResultSets and closes everything — all through the same java.sql interfaces. It removes the repetition, not the protocol, and everything you know about parameter binding, result-set iteration and transactions still applies.
Q33. How do Maven dependencies relate to database-driver availability?
A driver is declared in pom.xml by groupId, artifactId and version. Maven resolves it and places it on the compile and runtime classpaths. The driver registers itself through META-INF/services/java.sql.Driver, and the shade plugin must be configured with ServicesResourceTransformer so that file survives being merged into an uber jar. Without it the classes are present but the registration is lost, and DriverManager reports no suitable driver.
Q34. Why is it a mistake to let the interface do the work?
Three consequences. The event-dispatch thread is blocked for the duration, so the window freezes. The logic cannot be tested without constructing a window. And SQL or file handling spreads across the interface code, so a change to the schema or the file format touches many classes. The project's rule — the interface asks, the engine decides, a worker executes, a snapshot reports — avoids all three.
Q35. How does the model stay consistent while workers mutate it and the interface reads it?
By publishing immutable snapshots. BasinSnapshot and its parts are records whose constructors copy every collection with List.copyOf and Map.copyOf. The interface therefore reads a value that cannot change underneath it, so no locking is needed on the event-dispatch thread.
Q36. Why does the domain package depend on nothing?
Because that is what makes it testable and reusable. With no import of Swing, files, SQL or threads, the model can be exercised in a plain unit test with no setup, and the same model could be driven by a different interface or by an automated harness. It is also why the dependency graph has no cycles.
Q37. Where exactly do the I/O, JDBC and Swing technologies meet in this application?
At two boundaries. The first is the accepted event: after the model processes an event, the engine fans out to the journal, the archive worker and the database queue. The second is the published snapshot: the engine hands an immutable value to every registered listener, whose first action is to post to the event-dispatch thread. Everywhere else the layers are deliberately ignorant of one another.
Q38. Why does the application need a transaction when recording a dispatch?
Because three related writes must succeed or fail together: the mission row, the resource-usage rows and the audit event. Without a transaction, a failure after the mission insert would leave a running mission with resources that were never deducted, so the resource board would be permanently wrong and the history would not explain why.
Q39. Why must every write in a transaction use the same connection?
Because a transaction belongs to a connection, not to a statement. Calling commit() on one connection has no effect on work done on another, so three repositories each opening their own connection would create three separate transactions and atomicity would be lost — while the code still looked correct.
Q40. Why is isolation not a problem in this application?
Because all database work runs on a single-threaded executor. There is exactly one writer, so there is never a second transaction to interfere with the first, and no isolation level or locking policy needs to be reasoned about.
Q41. What happens to the application if the database is unavailable?
Four things, and all four matter. The application still starts, because availability is checked rather than assumed. The history panel shows an empty list and a status message. Every write becomes a no-op because enqueue returns early. And the file layer is entirely unaffected, so the log, archive, snapshot and reports are still produced.
Q42. Why does a reading reach the database only when the model changed?
Because BasinZone.apply rejects a reading whose tick is not newer than the last one applied, returning false. The engine writes to the database only when the model changed, so a duplicate or out-of-order observation is not recorded as though it had taken effect. The stale guard in the domain is therefore what makes the history accurate.
Q43. Explain the shutdown sequence and why the order matters.
Stop the producer, close the writer, join the intake thread, close the queue. Closing the writer is what makes the consumer's readLine() return null and its loop end. Joining the consumer before closing the queue ensures accepted events are drained rather than discarded. Closing the writer before stopping the producer would make the producer throw a spurious error, and never closing the writer would leave the consumer blocked forever.
Q44. Why is inheritance used so little in this project?
Because composition is more flexible and less coupled. The two uses are both framework contracts: SensorFeed extends Thread because a feed genuinely owns a thread's lifecycle and needs a name and priority, and the Swing panels extend JPanel and JFrame because Swing requires it. Everywhere else, objects are composed — BasinEngine has an executor, a buffer and a service rather than being one.
Q45. What is the difference between invokeLater and invokeAndWait?
invokeLater queues a runnable on the event-dispatch thread and returns immediately, so the calling thread continues. invokeAndWait queues it and blocks until the event-dispatch thread has run it — which is a deadlock if called from the event-dispatch thread itself. BasinWatch uses invokeLater exclusively.
Q46. Why does the project not use SwingWorker?
Because the engine must work without a user interface, so its operations cannot depend on a Swing type. Returning CompletableFuture keeps the engine independent of Swing and lets the interface choose how to consume the result. SwingWorker is more convenient inside a UI; a future is more flexible outside one.
Q47. Is a database always better than a file?
No. For a single-user desktop application a database adds a dependency, a schema and a failure mode. BasinWatch treats its database as optional precisely because the file layer already satisfies the essential requirements. The database earns its place by enabling selective queries and aggregation, not by being more modern.
Q48. Why does BasinWatch not use Spring?
Because for an application of this size the trade is unfavourable. There are six packages and roughly two dozen classes, wired by hand through constructors. Spring would add several dependencies, a component scan and a class of runtime errors in exchange for saving perhaps thirty lines of wiring. It would also make the database layer depend on a framework, when the project's aim is to show raw JDBC.
Q49. What is the single most important design decision in the project, and why?
The publication of immutable snapshots. It is what allows background threads to mutate the model while the event-dispatch thread renders it, with no locking in the interface and no possibility of a torn read. It is also what keeps the interface's job small — render a value, collect intent, report an outcome.
Q50. If you had to change one thing about this architecture, what would it be?
A defensible answer names a real trade-off rather than a fault. For example: the database schema declares the mission relationship as a plain column rather than a foreign key, which means a deleted mission could orphan its resource rows; enabling PRAGMA foreign_keys and declaring the constraint would fix it. Or: history is retained indefinitely, so a retention or archival policy would be needed before the database grew without bound. Naming a specific consequence is what makes the answer credible.

E.1Output prediction

Exercise 1 · What does this print?
try (ByteArrayOutputStream buffer = new ByteArrayOutputStream();
     DataOutputStream out = new DataOutputStream(buffer)) {
    out.writeInt(4);
    out.writeUTF("AB");
    out.writeDouble(1.0);
    out.flush();
    System.out.println(buffer.size());
}
Answer. The size is 16 bytes. writeInt contributes 4, writeUTF("AB") contributes 2 length bytes plus 2 character bytes, and writeDouble contributes 8. The lesson is to count from the format rather than guess: a data stream has no field metadata, so these sizes are the only thing that makes the layout predictable.
Exercise 2 · What does this print?
String line;
int count = 0;

    }

Answer. 3. The string contains two newline characters and therefore three lines: a, b and c. The final line has no trailing newline, and readLine() still returns it — the fourth call then returns null.
Exercise 3 · What does this print, and why is it surprising?
PipedWriter writer = new PipedWriter();
PipedReader reader = new PipedReader(writer);
writer.write("hello");
writer.close();
System.out.println(reader.read());
System.out.println((char) reader.read());
Answer. It prints 104 then e. The surprise is that read() on a character stream returns the character's numeric code, not the character — which is exactly why the return type is int. The rainfall contribution is 10.0 × 0.0014 = 0.014; the observed rise is 4.0 / 100 = 0.04; their sum is 0.054; multiplied by the reinforced-levee factor 0.58 gives 0.03132; added to 5.0 gives 5.03132, which is already inside the 0 to 8 clamp. Exercise 6 · How many statements execute, and how many commits?
connection.setAutoCommit(false);
try (PreparedStatement a = connection.prepareStatement("INSERT ...");
     PreparedStatement b = connection.prepareStatement("UPDATE ...")) {
    a.executeUpdate();
    b.executeUpdate();
    connection.commit();
}
Answer. Two statements execute and one commit occurs. With autocommit off, neither statement is durable until commit() is called; both become visible together at that moment. If the second statement threw, a rollback would discard the first as well — which is the whole purpose of the transaction.
Exercise 7 · What is wrong with this loop, and what does it print?
try (PreparedStatement ps = connection.prepareStatement(
        "SELECT zone_id FROM sensor_readings LIMIT ?")) {

            System.out.println(rows.getString(1));
        }
    }
}
Answer. The parameter is bound with setString for a LIMIT, which expects a number. Depending on the driver this either fails or produces an implicit conversion; the correct call is setInt(1, 10). E.2Debugging and repair

Exercise 8 · Repair this method.
public String readFirstLine(Path path) {
    BufferedReader reader = new BufferedReader(new FileReader(path));
    return reader.readLine();
}
Answer. Three problems: the reader is never closed, the charset is the platform default, and the method declares no checked exception. A corrected version:
public String readFirstLine(Path path) throws IOException {
    try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
        return reader.readLine();
    }
}
Note that returning from inside a try-with-resources still closes the resource.
Exercise 9 · Repair this loop.
String line = reader.readLine();
while (line != null) {
    process(line);
    line = reader.readLine();
}
Answer. This is actually correct — it reads before the loop and again at the end, which is the classic pre-read form. The repair is not about correctness but about clarity and duplication: 
String line;
while ((line = reader.readLine()) != null) {
    process(line);
}
The single-expression form makes it impossible for the two read sites to diverge, which is the real risk in the original.
Exercise 10 · Repair this queue method.
public synchronized BasinEvent take() {
    if (events.isEmpty()) {
        wait();
    }
    return events.removeFirst();
}
Answer. Three defects: wait() is not inside a loop, so a spurious wake-up or a competing consumer can empty the deque again; the method does not declare InterruptedException; and a closed empty buffer would wait forever. Corrected:
public synchronized BasinEvent take() throws InterruptedException {
    while (events.isEmpty() && !closed) {
        waitingConsumers++;
        try {
            wait();
        } finally {
            waitingConsumers--;
        }
    }
    if (events.isEmpty()) {
        return null;                 // closed and drained
    }
    BasinEvent event = events.removeFirst();
    notifyAll();
    return event;
}

    eventBuffer.close();
    feedWriter.close();
    sensorFeed.requestStop();
}
Answer. The order is wrong on two counts. Closing the queue before the consumer has drained it discards events already read from the pipe, and closing the writer before stopping the producer makes the producer throw a spurious IOException on its next write. Corrected order: requestStop(), then feedWriter.close(), then join the intake thread, then eventBuffer.close().

public void record(Connection a, ResponseMission mission) throws SQLException {
    try (Connection b = database.openConnection()) {

    this.entries = entries;
}
Answer. Two problems. The list is stored by reference, so a later change on the database thread could be visible to the event-dispatch thread mid-paint. And the table is never told the data changed, so it would keep displaying the old rows. Corrected:
void setEntries(List<DatabaseHistoryEntry> entries) {
    this.entries = List.copyOf(entries);
    fireTableDataChanged();
}

E.3Tracing and data flow

Exercise 16 · Trace a malformed record.

A line arrives from the pipe reading READ|abc|MIL-ST-2|MIL|12.4|3.1. Describe every consequence.

Answer. SensorReading.parse splits the line into six fields and finds the READ marker, so the field-count check passes. Long.parseLong("abc") then throws NumberFormatException, which the method catches and rethrows as IllegalArgumentException. SensorIntake catches that, reports a warning through the warning consumer, and executes continue. The event never enters the buffer, no worker sees it, no activity is recorded, no archive record is written, no database row exists. The intake loop continues with the next line.
Exercise 17 · Trace a stale reading.

Zone MIL has already applied a reading with tick 214. A duplicate arrives with tick 214. Describe every consequence.

Answer. BasinZone.apply compares reading.tick() <= lastReadingTick and returns false without changing any field. The model produces no activity message, so the journal writes nothing for it; the engine's changed test fails, so no archive record and no database row are written. The interface is unchanged. The only trace is that the intake accepted and queued an event that the model declined — which is correct, because the intake's job is to validate the format, not the ordering.
Exercise 18 · Trace a dispatch that fails its reservation.

The operator requests a pump deployment for zone NOR, but all four pumps are already committed. Describe every consequence.

Answer. ResourceAllocator.tryReserve checks every requirement and finds PUMP unavailable, so it returns false having changed nothing — no resource was partially deducted. BasinModel does not create a mission, no snapshot changes, and the interface's resource board is unchanged. The engine reports a failure message, which the listener posts to the event-dispatch thread and the status bar displays. Nothing is written to the log or the database, because nothing happened. This is the all-or-nothing property in action.
Exercise 19 · Trace a dispatch whose third database write fails.

In recordDispatch, the mission insert succeeds, the resource rows succeed, and the audit event insert throws SQLException. Describe every consequence.

Answer. The catch block calls connection.rollback(), which discards the mission row and the resource-usage rows as well. The exception is then rethrown and caught by the outer catch, which reports it through the status listener. The database therefore contains none of the three writes, so it agrees with the in-memory model, which did record the dispatch. That divergence is a real limitation worth naming honestly: the interface and the log show the dispatch, the database does not, and the status message is what tells the operator. A production system would reconcile on the next start.
Exercise 20 · Trace a session restore with a truncated file.

The file last-session.bws is 2,000 bytes but was truncated mid-object. Describe every consequence.

Answer. The size gate passes, because 2,000 bytes is below the 4 MB bound. The class filter approves the classes it sees. The version check passes, because the header was written first and is intact. readObject then throws EOFException — a subclass of IOException — because the stream ends inside an object. The load fails, the exception propagates to the caller, and the engine reports it. The application starts with a fresh model rather than a corrupt one, which is the correct outcome: a partial session is worse than none.
Exercise 21 · Trace a history read when the database file is deleted between launches.

Describe the sequence from start-up to an empty history table.

Answer. DatabaseManager.isAvailable calls openConnection, and because SQLite creates a missing database file on demand, the connection succeeds — so availability is actually true, and the initialiser recreates the four empty tables. loadHistory therefore returns an empty list from a real query rather than from the unavailable branch. The table shows no rows and the status reports zero entries. The distinction matters: an empty database and an unavailable database produce the same visible result through different code paths.
Exercise 22 · Trace a shutdown during a save.

The operator clicks Save and immediately closes the window. Describe what survives.

Answer. Two save operations may be in flight. The explicit save writes to name.bws.tmp; the shutdown's automatic save writes to last-session.bws through its own temporary file. Both run on basin-control, which is single-threaded, so they are serialised rather than concurrent. closeEngine stops the feed, closes the pipe, joins intake, drains the archive queue and flushes the journal. If the process is killed before either save completes, the temporary files are incomplete but the previous last-session.bws is intact, because the move had not happened. That is the purpose of the atomic replace.

E.4Architecture interpretation

Exercise 23 · Why is the archive written on a separate thread from the journal?
The journal is a character stream that the engine appends to directly, and it flushes on a policy. The archive is a byte stream with a header that must be written exactly once and typed records that must not interleave. Writing both on the worker thread would make every event wait for two disk operations. Putting the archive behind a single-threaded executor means the worker's cost is a queue insertion, while the header-once and no-interleaving guarantees are still upheld because there is only one archive writer.
Exercise 24 · Why does the engine publish snapshots rather than letting the interface read the model?
Because the model is mutated by three worker threads while the event-dispatch thread renders. Letting the interface read live objects would require the model's monitor to be held during painting, which would block every worker for the duration of a repaint and could deadlock if a listener ever called back into the model. An immutable snapshot removes the shared state entirely: the interface reads a value that cannot change, so no locking is needed and no torn read is possible.
Exercise 25 · Why does the database layer have both a service and repositories?
The service owns concerns that are not about any one table: the worker thread, the availability flag, the queue, the transaction boundaries and the failure reporting. The repositories own concerns that are about exactly one table: its SQL and its row mapping. Merging them would put transaction logic in every repository and SQL in the service; separating them means a repository can be tested against a plain connection with no threads involved, and the service's policy can change without touching any SQL.
Exercise 26 · Why is the sensor feed a Thread subclass while the intake is a Runnable?
The feed owns a lifecycle: it is started, it sleeps between intervals, it must be interruptible, and it holds a blocking pipe endpoint that must be closed. Extending Thread lets it carry a name, a priority and a state that diagnostics report. The intake is a task — a unit of work — with no lifecycle of its own; the engine creates a plain thread, names it, and hands it the task. This is the standard advice to prefer Runnable unless you must own the thread, applied where it genuinely differs.
Exercise 27 · What would break if the model were not thread-safe?
Three workers call model.process concurrently, and the event-dispatch thread reads snapshots. Without the monitor on process and the immutable snapshot boundary, two workers could apply readings to the same zone simultaneously, producing a lost update — one water level overwriting the other. The resource allocator could also over-allocate, because two dispatches could both pass the check loop before either decremented. Both failures are intermittent and load-dependent, which is exactly why the design avoids them structurally rather than by testing.
Exercise 28 · Why is the resource allocator's reservation all-or-nothing rather than incremental?
Because a mission requires several resources, and a partial reservation is a state the system cannot act on: the mission cannot start without all of them, and the deducted resources cannot be used by anything else. Incremental deduction would require a compensating rollback if a later requirement failed, and that rollback is itself a place where a bug could leave the inventory wrong. Checking everything before changing anything means no intermediate state exists to be cleaned up.
Exercise 29 · Why does the engine have three response workers but one archive worker and one database worker?
Because the three kinds of work have different constraints. Applying an event to the model is CPU-bound and independent per event, so concurrency helps. Appending to the archive must be serialised, because the header is written once and records must not interleave. Database work must be serialised for two reasons: SQLite permits one writer, and a single writer means no transaction can interfere with another, so no isolation policy is needed. The thread counts follow from the constraints, not from a guess about performance.
Exercise 30 · If you replaced SQLite with PostgreSQL, what would change?
Five things, and none of them is in the domain or the interface. The Maven dependency changes from org.xerial:sqlite-jdbc to the PostgreSQL driver. The URL changes from jdbc:sqlite:path to jdbc:postgresql://host:port/database with credentials. The DDL changes, because AUTOINCREMENT is SQLite syntax and the corresponding PostgreSQL type is different. Connections would need pooling, because a server round trip is far more expensive than opening a local file. And isolation would become a real concern, because a server database allows concurrent writers — so the single-writer guarantee the current design relies on would need replacing with explicit transaction handling. Everything else — the repositories' SQL shape, the prepared statements, the row mapping, the service, the interface — is unchanged, which is the payoff of programming to the JDBC interfaces.

G.3Ten mistakes that cost marks

  1. Concatenating values into SQL. Use PreparedStatement with placeholders. Always.
  2. Assuming deserialization validates. It bypasses constructors, so the rules you wrote in them do not run. Validate the restored state explicitly.
  3. Forgetting the append flag. Opening a file for output truncates it. A journal that should grow will silently restart.
  4. Omitting the charset. The platform default differs between machines, so a file written on one may be unreadable on another.
  5. Mixing up the end-of-stream signals. read() returns -1; readLine() returns null.
  6. Using wait() in an if. It must be a loop, because a woken thread is not guaranteed its condition holds.
  7. Confusing wait() with sleep(). wait() releases the monitor; sleep() does not.
  8. Returning a ResultSet from a method that closes its connection. Map rows into your own objects before leaving the block.
  9. Touching Swing from a background thread. Wrap the whole component-accessing body in invokeLater.
  10. Spreading several statements across different connections and calling it a transaction. A transaction belongs to one connection.

THE LAST WORD
  • Architecture first. Name the layers, the threads and the two boundaries before any API.
  • Three properties describe every stream. Direction, unit, and source or destination.
  • Four defences protect deserialization. Size, filter, version, validation.
  • One rule governs Swing. Only the event-dispatch thread touches components.
  • One connection owns a transaction. Everything inside it must share that connection.
  • Two persistence mechanisms, two questions. A file records; a database answers.
  • Explain connections, not definitions. That is what this book has been for.
